# 2.0.0 — Build wide, integrate once

Status: PROPOSED, 2026-10-01. Nothing below is built. Chris approves the cut list before a lane starts.

## The problem

The kit makes building fast and integration slow. Each fix moved a cost and added a guard. No fix
removed a step. The ledgers show it (September 2026, `kind: gate` and `kind: verify` rows):

| | NullBound | Trail |
|---|---|---|
| gate minutes | about 8,300 | about 560 |
| `make check` runs | 3,592 | 285 |
| `precommit` runs (avg) | 335 (256 s) | 100 (43 s) |
| `unit` runs (avg) | 5,019 (23 s) | 640 (12 s) |
| close-belt rungs (`verify` story + feature) | 676 rows, 681 min | 194 rows, 55 min |
| subagent dispatches recorded | 24, 443 min | 11, 458 min |

NullBound's agents spent more minutes in gates than in dispatches. The lead re-proved the
builders' work: 2,115 lead gate minutes against 2,358 for all builders (NullBound audit,
`nullbound/pm/roadmap/notes/ms-biomes/sdlc-audit-2026-10-01.md`). On 2026-10-01 the conveyor
refused 11 times before real work started. This session hit the same refusal: the dispatch guard
refused three read-only research agents.

The kit is 29,902 lines of source and 46,432 lines of tests. It installs 10 hooks. Four of
them run on every Bash call or every stop. The hooks gate, and the agents also gate, so most
work is proven two or three times.

## The model

**The PM tree is packed context.** It holds the work, its state and its record. It infers
nothing and it does not police. The flow has three roles:

1. **Architect (the lead).** It talks to Chris. It writes a story with `pm new story` and a
   body. It moves the story with `pm story building <id>`. It sends a builder with
   `dispatch --grain <id>`, which prints the brief.
2. **Builder (an arm).** It works in its own worktree on `feat/<slug>`. It runs the **spot
   check** (`[verify] spot`: lint and one unit slice, under 30 s). The pass is a receipt. It
   commits, pushes `feat/<slug>`, reports and stops. It runs no wide gate, opens no PR and
   merges nothing.
3. **Integrator (the lead, or one agent the lead sends).** It runs
   `agentic-sdlc integrate <slug>...` once per batch:
   1. make an `integrate/<batch>` worktree from the milestone branch;
   2. merge each `origin/feat/<slug>` with `--no-ff`, and run `[integrate] per_merge`
      (cheap: parse, lint) after each merge;
   3. run `[integrate] proof` ONE time over the batch (check + full unit + the changed
      integration slice). Target: 2 to 3 minutes;
   4. on green: fast-forward the milestone branch, write `done` on every story whose branch
      merged, delete the lane worktrees and branches (local and origin);
   5. on red: stop, name the lane whose files the failure touches, close nothing.

**Validate once.** A PASS is a receipt keyed on the tree. Nothing re-runs a gate on a tree that
has a receipt. A close, a push and a release write status and run no gate. CI runs the full tiers
one time, on the release PR.

**Reviews are a judgement, not a step.** The lead sends one reviewer over a batch when the risk
asks for one (state, schema, persisted format, input). A finding is a bug in the tree. A close
does not read a review record.

## The hook rule: hooks guard, agents do not re-check

Chris asked for one side, not both. The choice: **a hook refuses only an act that cannot be
undone or that harms another tree. A hook never runs a gate.** Agents commit and stop. The
integrator's one proof catches the rest.

## Appendix: the 2.0.0 SDLC (draft)

```text
# The SDLC — build wide, integrate once

The PM tree holds the work, its state and its record. It infers nothing.

## Roles
architect   writes stories, moves them, dispatches builders, integrates batches, releases
builder     one story or lane, its own worktree on feat/<slug>; spot check, commit, push, report, stop
integrator  the architect, or one agent it sends: `integrate` a batch, prove once

## The loop
1. pm new story <id> --body ...       the story file is the brief
2. pm story building <id>             it is in flight
3. dispatch --grain <id>              print the brief; start the builder with it
4. builder: edit; `make spot`; commit; git push -u origin feat/<slug>; report; stop
5. integrate <slug>...                merge the batch, prove once, write `done`, delete the lanes
6. release <version>                  every feature done; write the milestone; CI runs the full tiers

## Validate once
A PASS is a receipt keyed on the tree. Nothing re-runs a gate on a tree with a receipt.
A close, a push and a release write status and run no gate.

## Hooks guard, agents trust
A hook refuses only an act that cannot be undone or that harms another tree. A hook never runs
a gate. A builder does not re-check what the integrator will prove.

## Reviews
One reviewer per batch, when the lead judges the risk needs one. A finding is a bug in the tree.

## Branches
main is the released product. A milestone has milestone/<version>-<slug>. A lane is feat/<slug>
from the milestone branch. The milestone merges to main by merge-commit PR when Chris calls it.
```
