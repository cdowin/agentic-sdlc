## Findings

### D1 — MAJOR — the motivating tree, at `pm validate`, still reports the cosmetic defect alone — `open`

The feature exists because a real adoption had a retired key and no flow and *"was told about the
retired key, which is the cosmetic one."* That tree, through the real entry point:

```
$ agentic-sdlc check pm          exit=2, 2 lines
  [check:pm] ERROR — this tree declares no flow: [pm.states.milestone], … ← FLOW FIRST. correct.
  [check:pm] ERROR — [pm] review_slug_fallback was retired and does nothing …

$ agentic-sdlc pm validate       exit=2, 1 line
  [pm] ERROR — [pm] review_slug_fallback was retired and does nothing …
  ^ the flow is not mentioned. This is the original bug, unchanged.
```

`cmd_validate` (`repo/pm/cli.py:1040`) calls `config_complaints(cfg)` and raises on it. It never
calls `missing_flow_defect` and never calls `all_config_defects`. `checks/pm.py:66-69` prepends the
flow for exactly this reason, with a comment saying so — *"the flow can be declared and the roster
still stale; report the whole set either way, in the same order"* — and `pm validate` is described
in its own comment as *"the same predicates `check pm` runs"* and *"the two readers a stale rule id
would silently narrow."* The two readers have narrowed, on the one defect the feature ranks first.

`load()` succeeds on this tree (flows are read lazily; `flow_of` refuses at the first category
question), which is why `pm validate` gets a `cfg` at all and reaches `config_complaints` with the
flow still missing. `pm status` on the same tree does report the flow, because it asks a category
question — so the package's three surfaces give three different answers about one tree.

### D2 — MAJOR — two defects inside `load()`, one reported — `open`

`all_config_defects` collects the flow, then the vocabulary keys, then wraps `load()` in a single
`try` and catches **one** `ConfigError`. `load()` raises rather than collects, so everything it
guards is still first-one-wins:

```
version_at = "whenever"  +  version_pattern = "nogroup"
  -> 1 defect:  [pm] version_pattern needs one capture group around the version itself
     (the bad version_at is invisible)

checks = []  +  version_pattern = "nogroup"
  -> 1 defect:  [pm] checks is empty — remove the key to take the default …

checks = []  +  version_at = "whenever"  +  [pm.scaffold.story]
  -> 1 defect:  [pm] checks is empty …          (three present, one reported)
```

Through `agentic-sdlc check pm` the last of these is a single line as well. Criterion 1 is *"reports
EVERY defect it found, not the first"*; for the class a consumer is most likely to produce — a
mistyped value — it still reports the first. The docstring's own framing (*"Everything `load()`
refuses, collected rather than raised at the first"*) describes a `load()` that yields defects; the
one that ships raises on them.

### D3 — MAJOR — a `load()` defect hides every `config_complaint` — `open`

`config_complaints` runs only in the `else` branch, so any `load()` failure suppresses the retired
checks, the retired keys and the retired sections entirely. The same tree, twice, one character
apart:

```
[pm] version_at = "whenever" ; checks = ["D8","D1"] ; review_slug_fallback = true ; [agents]

$ agentic-sdlc check pm       exit=2, 1 line
  [check:pm] ERROR — [pm] version_at must be one of start ship, got 'whenever' …

… fix version_at, change nothing else …

$ agentic-sdlc check pm       exit=2, 3 lines
  [check:pm] ERROR — [pm] checks names D8, which was retired — became R5 …
  [check:pm] ERROR — [pm] review_slug_fallback was retired and does nothing …
  [check:pm] ERROR — [agents] was retired and does nothing …
```

One fix, three defects revealed. That is the round trip the feature was filed to remove, and the
`[agents]` and `D8` lines are the ones a consumer bumping the pin is most likely to be carrying —
the previous review's F7 landed the D8 retirement precisely so that a consumer naming D8 is *told
where the rule went*. A tree with any other value error is not told.

`config_complaints` needs nothing from a successfully-loaded config except `cfg.checks`, which is
readable from the section — so the ordering is a structural choice, not a constraint.

### D4 — MINOR — `pm validate`'s multi-defect output is one message, not one line each — `open`

```
$ agentic-sdlc pm validate      (3 defects)
  [pm] ERROR — [pm] checks names D8, which was retired — became R5 …
           [pm] review_slug_fallback was retired and does nothing …
           [agents] was retired and does nothing …
```

`cmd_validate` raises a single `Usage('\n         '.join(stale))`, so only the first defect carries
the `[pm] ERROR —` prefix; `check pm` prefixes each. Criterion 1 says *"one line each"*, and
CLAUDE.md hard rule 6 says output line shapes are grepped by consumers — a consumer counting
`[pm] ERROR` here gets 1 of 3.

### D5 — NIT — §6: three new cases in a new class, beside the exit-2 family the last review chose deliberately — `open`

The three cases landed as `AConfigErrorIsComplete` in `tests/test_pm_gate.py`. `ConfigValueErrors`
is at `tests/test_pm_gate.py:810` in the same module, and is where the previous review's **F8** was
landed one commit earlier with the explicit note *"in the exit-2 family, where §6's amend-first
ordering puts it."* This feature's story `existing?` column reads *"new — every refusal was covered
SINGLY, which is the gap"* and names no case it considered amending.

A separate class is arguable — "several defects at once" is a different subject from "one bad value
is exit 2" — but §6 requires the reviewer to ask, and the record does not answer. The repo
established the home for exit-2 config cases and the next feature did not use it or say why.

## What I could NOT make happen — the brief asked, so here is the answer

The brief asked whether `all_config_defects` **reports a defect that is not real, or duplicates
one**. I probed both directly and **found neither**.

- **Duplication.** Every `VOCABULARY_KEYS` entry (`milestone_states`, `feature_states`,
  `story_states`, `bug_states`, `also_done`) is *also* in `RETIRED_KEYS`, and the two sweeps word
  the message differently — *"was retired and is refused"* vs *"was retired and does nothing"* — so
  a duplicate looked likely. It cannot happen: `load()` raises on a vocabulary key
  (`model.py:291-294`) with a string identical to the one the first sweep produced, so the exact-match
  dedup catches it, and `config_complaints` never runs on that path at all. Measured with one
  vocabulary key, with two, and with a vocabulary key plus a missing flow: 1, 2 and 2 defects, no
  repeats.
- **A defect that is not real.** Every line in every multi-defect run above corresponds to something
  actually wrong with the tree. The substring guard `not any(said in seen for seen in out)` is
  loose enough to be worrying, but I could not construct a config where a real defect is a substring
  of another and gets swallowed.
