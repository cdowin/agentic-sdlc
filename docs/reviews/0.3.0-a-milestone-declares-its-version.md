## Findings

### F1 — MAJOR — `pm retire` makes R5 demand a version regression — `open`

`release_is_shipped` decides "has this shipped?" by resolving the version to a **live milestone
record** and reading its status. `pm retire` **deletes** that record (`cli.py:585`,
`plan.delete_tree(mdir)`; the verdict line is *"retired — … removed"*). So retiring a finished
milestone flips its `order` entry from shipped back to unshipped, and under the default
`version_at = "start"` that entry becomes *current* again.

Measured end to end, plan `["0.0.9", "0.1.0"]`, version file at `0.1.0`:

```
before retire (healthy)          current='0.1.0'   check pm exit=0
pm retire shipped                exit=0  — pm/roadmap/shipped-m removed
AFTER retiring the shipped one   current='0.0.9'   check pm exit=1
  DRIFT  pyproject.toml version '0.1.0' does not match the current release '0.0.9'
         (no milestone claims it — an `order` entry nothing carries) …
```

Two shipped verbs disagree, and the rule that loses tells the consumer to move the version file
**backward**. The parenthetical is also false in substance: a milestone did claim `0.0.9` and did
ship it; its record was retired. The same happens for `zz_archive` (`known_milestones` walks
`milestone_walk`, which excludes the archive), and it mirrors under `version_at = "ship"`, where the
shipped list shrinks and current goes backward or vanishes into the WARN of F3.

`test_an_entry_no_milestone_claims_has_not_shipped` shows the builder decided deliberately that the
resolver "must not step over" an unclaimed entry, deferring dangling entries to R1 in
`the-plan-and-the-tree-agree`. That reasoning is right for an entry **never** claimed and wrong for
one whose claimant was retired — the two are indistinguishable to `release_is_shipped`, and only the
second is a normal lifecycle event.

### F2 — MAJOR — duplicate `version:` claims resolve by directory sort order — `open`

`milestone_of_version` returns the **first** claimant and `release_is_shipped` reads only that one.
`milestone_walk` is `sorted()`, so the tiebreak is the directory name. Same facts, opposite verdicts:

```
two milestones claim 0.0.9; 'a' done, 'b' building   -> current='0.1.0'  exit=0
two milestones claim 0.0.9; 'a' building, 'b' done   -> current='0.0.9'  exit=1
```

Renaming a directory flips the gate. Hard rule 9 says a malformed declaration is refused at exit 2;
this one is silently resolved in favour of whichever record sorts first. `version_claims`'s own
docstring says it returns a list rather than a dict *"because R3 asks whether two milestones claim
the same version, and a dict would have eaten the duplicate"* — the shape was kept for the question,
but nothing in this range asks it, and R5 ships before R3 does.

### F3 — MAJOR — R5 prints PASS with a false reason over a plan it could not read — `open`

Six shapes of `releases.md`, R5 enabled, all producing the identical line and **exit 0**:

```
releases.md absent                            exit=0   WARN … declares no `order`
releases.md present, frontmatter BOM-damaged  exit=0   WARN … declares no `order`
releases.md present, closing fence eaten      exit=0   WARN … declares no `order`
releases.md present, order is a SCALAR        exit=0   WARN … declares no `order`
releases.md present, key misspelled `oder`    exit=0   WARN … declares no `order`
releases.md is undecodable bytes              exit=0   WARN … declares no `order`
```

Only the first is true. In three of the others the file **does** declare `order` and the reader
could not reach it; in the sixth the gate never decoded the file at all (`list_field_of` swallows
`OSError` and `UnicodeDecodeError` and returns `[]`). This is rule 4's first cardinal sin: a verdict
line asserting a fact about content the gate never established, at exit 0.

The deliberate decision recorded in `_release_findings` — *"a tree mid-adoption has no plan yet;
reddening it would be milestone risk 1"* — covers the **absent** file and is right. The other five
ride along on it for free. The repo already has the vocabulary for exactly this class: `DAMAGE_FORMS`
(`bom` / `blank-line` / `no-closing-fence`) exists because damaged frontmatter must be a finding
rather than a note on every other grain document, and this feature's own words call `releases.md`
grain-shaped. The PASS verdict line also never names R5 as ungraded — `PASS — no PM-tree status
drift; scanned N milestone(s), …` — where V1-V6 carry a census for precisely this reason.

### F4 — MINOR — the no-parser gate misses the two likeliest regrowth sites — `open`

The gate **does** bite, and I proved each half against a scratch copy of `src`:

```
RENAME current_release -> current_release_v2        FAIL  ('current_release' not found)
RENAME _release_findings -> _grade_release          FAIL  ('_release_findings' not found)
PLANT split()+int() inside current_release          FAIL  (offender line, both shapes)
PLANT `import packaging` in model.py                FAIL  (comparator gate)
surface dict cut from 8 names to 7                  FAIL  (7 not >= 8, census floor)
surface dict cut to 1 name                          FAIL  (1 not >= 8)
```

So the name-existence assertions and the census floor both hold, and the floor is exactly tight (8
names, floor 8) rather than slack. The narrowing is honest about its **size**. It is not honest about
its **label**. Two plants pass both gates:

```
PLANT split()+int() in conveyor/steps.py:check_version_sync   PASS   <- not scanned
PLANT int() in model.shipped_version                          PASS   <- not scanned
```

`check_version_sync` is the release belt's version comparator — the single most likely place for
"did the version increase" to grow back — and `shipped_version` is the reader that pulls the version
out of the version file. The docstring calls the scanned set *"the modules that HANDLE versions"*;
it is 8 functions in 2 files, and the whole `conveyor/` package, where `release <version>` lives, is
outside it. The absence holds there today (I read it: `check_version_sync` compares with `!=`,
`version_defect` checks length/whitespace/literal-segment, neither parses), so this is a coverage
gap, not a live defect.

### F5 — MINOR — `current_release`'s docstring is false in both halves — `open`

> *"By construction this is never zero-or-several the way 'the one milestone in progress' was: it
> does not read a status field at all."*

It reads `status` one call away, in `release_is_shipped`, and F2 shows it **is** several — silently
resolved rather than refused. Story 01's `## Close` note repeats the claim verbatim. SDLC §5 requires
adversarial cases against every "never" and "cannot" in a docstring; this absolute has none, and it
is the one claim in the new code that is untrue.

### F6 — MINOR — a blank line silently truncates the plan — `open`

`list_field_of` breaks on the first line that is not a list item, so a blank line between entries
drops every entry below it, with no complaint:

```
order:\n  - "0.0.9"\n\n  - "0.1.0"    ->  ['0.0.9']
```

R5 then grades against the wrong current release and reports a confident mismatch. `releases.md` is
the file `pm order --append` will be editing on every ship, and visually spacing a long plan is the
obvious thing a human does to it. Related, lower: a deeper-indented nested item is flattened into a
sibling (`- "0.0.9"` / `    - "sub"` / `- "0.1.0"` reads as three entries).
