### Criterion 2 — the claim line is unconditional, and I tried to break it

```
no claim, no drift        ok: installables-current — 28 installed file(s) are current with 0.2.0
                          (no clause — deliberate: rule 5, byte-identical to a repo with no
                           devkit.toml)

drift, no claim           error: … 1 of 28 installed file(s) differ from what 0.2.0 ships:
                          .github/workflows/verify.yml (differs; `agentic-sdlc install-ci --diff`)

                          1 claimed by [adopt] ours and not graded: .github/workflows/verify.yml

2 drifted, 1 unplanned    error: … 2 of 28 … differ …; 1 claim(s) in [adopt] ours name no file
claim                     0.2.0 installs: no/such
```

**The drift does not hide.** Claiming the file moves it out of the FAIL, but the census drops 28 →
27 in the same sentence and the file is named by path in the clause beside it. A reader comparing
two runs sees the count move. That is what risk 2 of the milestone record asked for, and it is
delivered.

**And it survives the clip.** `_claim_clause` is concatenated **after** `_clip(...)` in both
branches of `check_installables_current`, and the count is outside the clip that applies to the
claimed list itself. Measured with all 28 files claimed: the line is 528 characters, the drift half
is clipped at 400 with `…`, and `28 claimed by [adopt] ours and not graded:` is intact at the front
of its own clause. A hundred drifted files cannot push the claim off the line.

## Findings

### O1 — MAJOR — claim everything and a zero census prints PASS — `open`

Two files genuinely drifted; `[adopt] ours` naming all 28 planned destinations:

```
[adopt] ok: installables-current — 0 installed file(s) are current with 0.2.0;
        28 claimed by [adopt] ours and not graded: .github/workflows/verify.yml,
        .github/workflows/semver-gate.yml, … .claude/agents/…
```

`ok`, on a check that graded **nothing**. Hard rule 4: *"Prove the census matches intent — a gate
scanning 0 files FAILS and says so."* This is that gate, and the verdict word a consumer greps for
is `ok`.

The mitigation the story chose — print the claim — does fire, and it is not nothing: `0 installed
file(s) are current` and `28 claimed` are both true sentences, and a human reading the whole line
can see what happened. But the story's criterion 2 treats printing as sufficient, and rule 4 is
about the **verdict**, not the prose beside it. `installables-current` is the check whose whole
purpose is that the consumer's installed files match the pin; a project that claims all of them has
turned it off, and the belt should say so in the word it decides with, not only in the clause after
the semicolon. The shape the repo already has for this is `Answer.unverifiable`, which `adopt` prints
and which does not read as a pass.

Where the line is: one claimed file out of 28 is a project owning a file, and `ok` is right. All 28
is a project with no check. I would not try to pick a threshold — `counted == 0` is the honest
boundary and it is the one rule 4 names.

### O2 — MAJOR — the census is 28 and the package installs 30 — `open`

`_installable_drift` iterates `install.PLANS`, which holds five verbs and 28 destinations.
`pm install-skills` is the sixth installer (CLAUDE.md's self-hosting list names it) and its two
destinations are in no plan. Measured on a consumer with **no `[adopt] ours` key at all**:

```
baseline                error: … 3 of 28 installed file(s) differ …

append junk to BOTH .claude/rules/pm-execution.md and
                    .claude/skills/pm-operations/SKILL.md

after                   error: … 3 of 28 installed file(s) differ …      <- unchanged
                        grep -c ours devkit.toml: 0

and pm install-skills --diff on the same tree:
  [install] .claude/rules/pm-execution.md exists and differs from what this would write
  [install] .claude/skills/pm-operations/SKILL.md exists and differs from what this would write
```

Two of the thirty files this package writes into a consumer can drift arbitrarily and the belt's
census does not move, does not name them, and does not count them. This predates the feature — but
the feature is what makes the census sentence load-bearing. Its entire argument is that an ungraded
file must be *visible*, and it built a clause to make claimed files visible; these two are ungraded
and invisible, and a consumer cannot even claim them, because a claim naming one would be reported
as *"name no file 0.2.0 installs"*.

`.claude/rules/pm-execution.md` is the file that tells a consumer's agents how to run the PM CLI.
It is the single worst file in the set to let drift silently, and it is one of the two.

### O3 — MINOR — `""` and `"."` pass the claim grammar — `open`

Criterion 5's refusal matrix, all eight shapes, on the belt:

```
ours = "astring"      exit 2  checks run 0   must be a list of strings …
ours = [7]            exit 2  checks run 0   must be a list of strings, got [7]
ours = ["../evil"]    exit 2  checks run 0   … it climbs out with a `..` segment
ours = ["/abs/path"]  exit 2  checks run 0   … it is absolute
ours = ["a\\b"]       exit 2  checks run 0   … it carries a backslash
ours = ["https://x"]  exit 2  checks run 0   … it is a URL
ours = [""]           exit 1  checks run 6   ACCEPTED
ours = ["."]          exit 1  checks run 6   ACCEPTED
```

Six refuse correctly, with zero checks run — the "before the first check" half of criterion 5 holds
exactly. SDLC §5's enumeration names "traversal, empty/dot segments, backslashes, globs, absolute
paths, schemes, whitespace, over-long strings"; **empty and dot are the two the grammar misses**.

The story's §5 note says `ours` "reuses `core/config.relpath_tuple` and the grammar's own matrix is
not re-spelled" — the right call under the 2026-09-05 amendment, and the reuse is real
(`steps.py:442`). The three `CONFIG_REFUSALS` rows are there, and their comment names the grammar's
matrix precisely: `tests/test_grain_shape.py::test_every_path_shaped_spelling_that_leaves_the_checkout_is_refused`.

**That matrix is scoped by its own name to spellings that LEAVE the checkout** — 11 of them,
`/tmp/elsewhere` through `https://…` — and `""` and `"."` do not leave it, so on its own terms the
reuse claim is defensible. But SDLC §5's enumeration of what an input surface owes reads
"traversal, **empty/dot segments**, backslashes, globs, absolute paths, schemes, whitespace,
over-long strings", and those two segments are refused by no key that goes through this grammar.
`relpath_tuple` is also `[doc] scope` and `[shell] roots`, so all three inherit it. **The fix
belongs in `_escapes_checkout` or in a second row of that grammar's matrix, not here**; the finding
is filed against this feature because this is the story that read the matrix as complete.

Note `ours = []` IS refused (`remove the key`) — the empty LIST is covered, the empty STRING inside
a list is not.

Impact today is small — an empty or dot claim matches no planned path, so it lands in the
"name no file 0.2.0 installs" clause rather than silencing anything. It is a grammar hole, not a
live hiding place.

### Observation — zero claims print no clause, deliberately

With no `ours` declared the line is `28 installed file(s) are current with 0.2.0` and there is no
claim clause at all. The brief asks whether the line is unconditional at zero claims; strictly it is
not. `_claim_clause`'s docstring gives the reason — *"Empty when nothing is claimed, so a repo
declaring no `ours` prints byte-identically to one with no devkit.toml at all (rule 5)"* — and that
is hard rule 5, which says a GATE ships stock defaults and a repo with no `devkit.toml` runs
byte-identically. Naming zero claims would break it for every consumer to say nothing. **Correct as
built**; recorded rather than filed so the next reader does not re-open it.

## What I did NOT verify

  the brief. The adopt module was run scoped, `-m shell`, and only that module.
- **`[release] ours` / `[story] ours` / `[feature] ours`.** `_ours_of` is keyed on the operation, so
  the claim works for any belt whose step list includes `installables-current`; only `adopt` has it

- **Whether O1's fix is `unverifiable`, a FAIL, or a threshold.** Three defensible answers; the
  ruling is not mine. What rule 4 settles is that `ok` at census 0 is not one of them.
- **Whether O2's fix is to fold the skills pair into `install.PLANS` or to grade it separately.**
  The pair is generated rather than copied and `resolve_body` may not reach it the same way, so the
  cheap-looking fix may not be the right one.

  `tools//dev/gdk_gate.sh`). `_installable_drift` matches claims by exact string against the plan's
  `rel`, so I expect such a claim to be reported as unplanned rather than to silence the file — the
  safe direction — but I did not run it.
- **I left `pm/roadmap/**` untouched** and ran no repo-wide git command.
