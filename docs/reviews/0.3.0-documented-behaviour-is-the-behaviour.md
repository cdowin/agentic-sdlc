## Findings

### X1 — MAJOR — the ledger REFUSED line still fires once per gate, per run — `open`

The story's `## How this is proven` table files criterion 3 as *"fixed upstream by
`the-ledger-binds-to-the-current-release`"*, **"confirmed gone"**. It is not gone. Driving the
shipped gate library (`tools/dev/gdk_gate.sh`, `gdk_gate_log` → `gdk_gate_capture` →
`gdk_gate_verdict`, exactly as `Makefile.devkit`'s `gdk_gate` recipe does) over a tree built by
`agentic-sdlc pm init` + `pm new milestone 1.0`, with no milestone flipped to `building`:

```
### THREE gates, ONE run, fresh adoption (no building milestone) ###
  [alpha] ok — full log: .gate-reports/alpha.log
  gdk-gate: the recorder exited 1: [pm] REFUSED — pm/roadmap/releases.md declares no `order`, …
            — no cost row for this gate
  [beta]  ok — full log: .gate-reports/beta.log
  gdk-gate: the recorder exited 1: [pm] REFUSED — … — no cost row for this gate
  [gamma] ok — full log: .gate-reports/gamma.log
  gdk-gate: the recorder exited 1: [pm] REFUSED — … — no cost row for this gate

### the same three gates after `pm milestone building 1.0` ###
  [alpha] ok   [beta] ok   [gamma] ok        (clean)
```

The original finding's words were: *"On a tree with no `building` milestone, each gate prints
`gdk-gate: the recorder exited 1: [pm] REFUSED — …`. On a fresh adoption that is once per gate, per
run, forever, and it reads like a broken install rather than a true and unremarkable fact."* Every
clause of that is still true. What changed is the **reason inside** the line — from *"no milestone
in pm/roadmap is in progress"* to *"pm/roadmap/releases.md declares no `order`"*.

The story's reasoning is scoped to a *phrase* rather than to the condition: *"the two remaining `is
in progress` refusals are `ledger record` (dispatch/session rows) and `ledger report`, neither of
which runs per gate."* But `ledger record --gate` **is** what runs per gate (`gdk_gate.sh:221`,
`argv=(pm ledger record --gate …)`), and `release_ledger_dir` carries its own refusal on the same
tree state. Measured directly:

```
pm ledger record --gate unit --verdict PASS --duration-ms 1000
  no building milestone, no releases.md   exit=1  [pm] REFUSED — … declares no `order` …
  after `pm milestone building 1.0`       exit=0  ledger gate row appended
  after `pm order --append 1.0`           exit=0  ledger gate row appended
```

Two exits from the state now clear it where one did before, which is a real narrowing and worth
saying. It is not the criterion. `_gdk_ledger_note` (`gdk_gate.sh:107-109`) is an unconditional
`printf` with no per-run dedup and no information wording, so *"reported once per run, as
information"* has nothing implementing it. The feature's own proof budget names two landing sites —
*"the CLI help/contract module **and the gate-library shell corpus**"* — and `6273959` touches no
shell file at all. The empty second landing site is this finding, visible in the commit stat.

### X2 — MAJOR — the zero census tests a different condition from the one it prints — `open`

`budget.py:198` guards on `if not rows:` — `rows` is **every row of the ledger, unfiltered**, while
the gate rows are the separate `gates` / `newest` maps built one line above. The verdict line it
prints says *"the current release's ledger holds no `gate` row at all, so nothing was graded"*.
Measured, ceilings declared throughout:

```
ceilings + ledger totally EMPTY                        exit=1  FAIL — … holds no `gate` row at all
ceilings + one `decision` row, ZERO gate rows          exit=0  UNMEASURED …
ceilings + one `dispatch` row, ZERO gate rows          exit=0  UNMEASURED …
ceilings + one `test` row, ZERO gate rows              exit=0  UNMEASURED …
ceilings + ONE gate row for an UNDECLARED tier (docs)  exit=0  UNMEASURED …
```

Rows 2-4 are the defect: not one `gate` row exists, nothing was graded, and the gate exits 0 while
its FAIL line — the one that would have told the truth — is suppressed by the presence of a row that
is not a measurement. This is rule 4's first cardinal sin (*a verdict asserting a fact the gate never
established*) sitting inside the guard added to enforce rule 4.

It is also the realistic path, not a corner. `pm ledger record` files `dispatch` and `session` rows
from the Claude Code hooks, and on a fresh adoption those land long before any gate runs — the exact
tree the feature was written for. The brief's question *"is one row enough to leave it?"* has a
sharper answer than intended: **one row of any kind, including kinds that are not measurements.**
`gates` is already computed and `if not gates:` is the condition the line describes.

The shipped case `test_one_gate_row_is_enough_to_leave_the_zero_census` passes a `gate_row`, so it
proves the boundary it names and cannot see this. Its docstring — *"the census is about whether
anything was READ"* — is the code's behaviour written down, and it disagrees with the verdict line.

### X3 — MAJOR — 21 is a roster; 5 are read and 2 are run — `open`

The count is right and the derivation is right: `help_surfaces()` walks the same two rosters
`routed_verbs()` asks plus `KNOWN_GATES`, so a new verb or gate joins with nothing to update. 21
surfaces enumerated, confirmed. What the module *claims* to do with them is where it parts from what
it does. Its own docstring: *"It enumerates every `--help` this package prints, extracts the exit
codes each one CLAIMS, and — for the claims a temp tree can realise — runs the condition and
compares."* Measured:

```
ROSTER                                    : 21 surfaces
WITH an exit contract the reader can find :  5 / 21
WITHOUT                                   : 16 / 21   <- never graded, silently
TOTAL claim-clauses across the corpus     : 14
Surfaces with a RUN probe                 :  2  (check budget, gates-extra)
Clauses actually RUN                      :  4 / 14
```

The 16 are not surfaces that state no exit codes. **Eleven of them document exit codes in prose the
reader cannot see**, because `_EXIT_CONTRACT` is case-sensitive and wants `Exit codes:` or `Exit:`
at the start of a line:

- `pm --help` — `EXIT CODE: 0 ready, 1 not ready — naming every blocker, never a tally — 2 usage`.
  A full three-code contract, in the surface this feature edited, and the reader returns `''` for it.
- `close --help` — `exit 1, no status written. --force writes …`
- all five `install-*` surfaces — `exits 1 because a replacement was withheld`
- `check shell --help` — `exit 0 when shellcheck is not installed. A zero census FAILS.`
- `check hooks --help`, `check pm --help`, `agentic-sdlc --help` — one apiece.

So the ship criterion — *"No `--help` in the package documents an exit code the code does not
return, held by a test that reads the help text and the exit code together"* — is held over
`check budget` and `gates-extra`. For the other nineteen the suite is green because it never looked.
This is the module's own stated sin (*"a hand-written roster in a test is the same defect one layer
down"*) with the roster replaced by a regex: derived correctly, then read by something that quietly
matches a quarter of it.

**The half that is right, and I tried to break it:** there is no restated expectation anywhere.
`ExitClaim` carries no expected code, and `claimed_code()` reads it out of `help_corpus()[surface]`,
which is the text of a live `cli.main()` run. The pair under test really is the documentation
against the binary. That part of the deliverable is sound.

### X6 — MINOR — a stray exit code is invisible when clauses are separated by periods — `open`

`_CODE_MARK` needs a code to be introduced by `[;|·,]` or to open the string. A help using sentences
files everything under the first code:

```
'Exit codes: 0 pass; 1 findings; 3 boom.'   -> claimed_codes = [0, 1, 3]   (caught)
'Exit codes: 0 pass. 3 boom. 7 worse.'      -> claimed_codes = [0]         (3 and 7 invisible)
'EXIT CODE: 0 ready, 1 not ready, 9 nonsense' -> NO CONTRACT FOUND         (all invisible)
```

`test_no_help_names_an_exit_code_outside_the_contract` is rule 6's guard, and both bottom rows walk
past it. The second row is the shipped spelling in `pm --help` (**X3**). Lower than X3 because no
current help uses the period form — but the reader's comment says a digit must be *"introduced
rather than merely present"*, and a full stop is how English introduces a clause.

## What is right, said plainly

- **The expected code is genuinely read at run time.** No `ExitClaim` carries one; `claimed_code()`

- **`check budget` does not redden this repo.** `uv run -q agentic-sdlc check budget` → `PASS`,
  exit 0, `within their time budget: test, unit; within their case limits: unit; unmeasured:
  integration; uncounted: integration`. The story's claim holds, measured.
- **§6 was honoured where it counts.** The budget half genuinely AMENDED
  `test_a_tier_with_no_row_is_UNMEASURED_and_never_a_pass` — adding two docstring assertions to the
  case that already owned this behaviour — instead of writing a parallel one. That is the ordering
  §6 asks for, and the amended case is where a future reader will look.
