# Milestone review — `0.3.0 the bump explains itself` — RELEASE-WITH-FIXES

Cross-cutting pass over `46f602e..HEAD` (39 commits, 11 features, 17 stories, 3 bugs), branch
`milestone/0.3.0-the-bump-explains-itself`, run 2026-09-06. SDLC close-protocol step 1.

**Nothing below was concluded from a diff.** The primary instrument is a scratch consumer built at
`v0.2.0` from `git archive v0.2.0`, wired with `agentic-sdlc init`, given a PM tree and a
`devkit.toml` that opts in to `D8` exactly as the v0.2.0 installable documents it, committed, and
then driven with the HEAD tree's CLI. Probe scripts: `mrev7_build.sh`, `mrev7_q.sh`,
`mrev7_ledger.py`, `mrev7_seams.sh`, `mrev7_surface.py`, in the agent scratchpad. The ten landed
per-feature reviews were NOT re-run; their findings are dispositioned and three were spot-checked.

**The tree moved under this review.** An eleventh feature,
`0.3.0/documented-behaviour-is-the-behaviour`, was `building` throughout, and its review record
arrived untracked mid-pass. See M7 — it is the release-blocking fact.

## The semver call — MINOR (0.3.0) is the right number, and the release is BREAKING

Hard rule 7: *patch = same interface; minor = a new verb, flag, config key or output shape; major =
a consumer Makefile or hook must change to survive.*

**Measured, not argued.** Every removal claim in this range was checked against `v0.2.0`:

| what could break a consumer | measured | result |
|---|---|---|
| a verb withdrawn | 40 CLI surfaces enumerated at both trees | none; HEAD is a strict superset |
| a flag withdrawn | every `--help` flag set, both trees | none; adds `--append --insert --before --remove` |
| a `Makefile.devkit` target withdrawn | target lists diffed at both trees | none added, none removed |
| an installable withdrawn | `git ls-tree` of `installables/` both trees | identical file set |
| `ROADMAP.md` deleted from a consumer | md5 before/after bump + `pm init` re-run | byte-identical, left alone |
| a grepped output shape | `grep -c '^\[install\]'` on `install-agents --diff` | 13 → 14 (grew) |

So nothing in rule 7's major clause literally fires: **no consumer Makefile and no consumer hook
must change.** `pm status` and `pm roadmap` still exit 0 with a retired `D8` in the roster, because
the roster is validated in `check pm` rather than `model.load()` — the work-moving verbs survive.

**But one thing does break.** A repo whose `devkit.toml` names `D8` — a configuration the v0.2.0
installable itself documented and invited — goes from green to a hard stop:

```
v0.2.0 :  check pm  -> [check:pm] PASS ... 5 warning(s)          EXIT=0
HEAD   :  check pm  -> [check:pm] ERROR — [pm] checks names D8,
                       which was retired — became R5 ...          EXIT=2
HEAD   :  check all ->                                            EXIT=2
HEAD   :  adopt     ->                                            EXIT=1
after removing D8 from the list, per the error's own instruction:  EXIT=0
```

`make check` fails. `make precommit` fails. CI fails. The consumer must edit a file to survive.
That is the *test* in rule 7's major clause, even though the artifact named in it is neither a
Makefile nor a hook — it is `devkit.toml`, which rule 5 makes the canonical consumer-owned surface
("Per-project variation is the consumer's `devkit.toml`"). Rule 7 has no tier for a retired config
VALUE: its minor list is four ADDITIONS, and an interface that SHRANK is on neither list.

**The gap resolves on the version number, not on the tier name.** This package is `0.x`. Calling
this MAJOR means `1.0.0`, which asserts a stable interface this package does not intend to assert
while `0.4.0` is already planned in `releases.md`. In `0.x`, the minor slot IS where a breaking
change is expressed. `0.2.0 → 0.3.0` is therefore correct.

**Conditions on that call, and I would not ship without them:** the CHANGELOG must say the word
BREAKING against the `D8` retirement — right now that fact sits in the middle of the first bullet,
five lines in, bolded but unlabelled — and rule 7's gap (a retired config value; no `0.x` carve-out)
should be recorded with `pm decide` so the next reviewer is not asked to re-derive this. Mitigating,
and it is real: the error names the retired key, the rule that replaced it, the config that selects
its behaviour, and the exact edit. It is the best-behaved breaking change this package could ship.

## What holds

**The conflation is fixed in the code, and fixed well.** `current_release()` is the release being
worked on and its docstring states in bold that it does not read `version_at`; `graded_release()` is
R5's question and reads it. I measured both on a two-entry plan (`0.3.0` done, `0.4.0` building):

```
version_at='start'  current_release=0.4.0  graded_release=0.4.0  ledger=0.4.0-in-flight
version_at='ship'   current_release=0.4.0  graded_release=0.3.0  ledger=0.4.0-in-flight
```

The version file is graded against `0.3.0` while the ledger and the belt stay on `0.4.0`. That is
the separation the milestone was built for. It survives in the code. It does not survive in the
CHANGELOG — M1.

**`[adopt] ours` is not a hiding place.** The milestone's own stated risk. Claimed files are named
in the check's own output on the PASSING path: `28 installed file(s) are current with 0.2.0; 2
claimed by [adopt] ours and not graded: .claude/agents/developer.md, docs/sdlc-protocol.md`. A claim
naming a file this version does not install is reported, not refused. A bare string instead of a
list is exit 2 with the fix spelled out — the `tuple(cfg.get(...))` trap CLAUDE.md names is avoided.

**The new rules do not print PASS over what they did not measure.** With R1-R6 enabled and no
`releases.md` in the tree, `check pm` says `R5 is enabled and pm/roadmap/releases.md declares no
'order' — nothing to grade pyproject.toml against` and `BACKLOG 1 milestone(s) declare no version:
(R2)`. The verdict is PASS-with-warnings, which is the milestone's declared design (the risks
section requires these be WARNs), and the ungraded rule says so by name rather than going quiet.

**`pm ready-for tag` is layered correctly, not lying.** It answers READY over ten records while an
eleventh review sits in the tree with eleven open findings — because it reads only records that
grains POINT at, and the eleventh feature carries no pointer yet. `ready_for.py:278` says so, and
`ready-for milestone` — the rung that must pass first — correctly blocks on that feature. Two rungs,
two questions; I went looking for rule 4's first sin here and did not find it.

**Dispositions spot-checked, three of 52.** `F1 landed 48bf6d5`, `C3 landed 04f2f5a`,
`A1 landed 3d21718` — each commit's diffstat touches the module the finding names. Every finding
HEADING in all eleven records ends `— open` while the table below carries `landed <hash>`: that is
the convention (the heading is the reviewer's text as raised, the table is the disposition after
landing), applied consistently, not a contradiction.

## Findings

### M1 — MAJOR — the CHANGELOG re-asserts the conflation the code fixed — `open`

`CHANGELOG.md`, `## Unreleased`, the ledger bullet:

> A cost row is filed against the first unshipped entry in `order` (**or the last shipped, under
> `[pm] version_at = "ship"`**), which answers with exactly one by construction and **reads no
> status field to do it**.

Both bolded claims are false. `release_ledger_dir()` (`model.py:1543`) calls `current_release()`,
which by design never consults `version_at`; measured above, `version_at="ship"` leaves the ledger
on the in-flight release while only the graded release moves. A consumer running bump-at-close —
which is what this repo itself runs (SDLC.md §1) — will look for cost rows in the last-shipped
milestone's ledger and not find them. This is the milestone's worst defect, fixed everywhere in the
code and surviving in the one document that is the consumer's whole view of the release.

The same sentence is wrong a second way: `release_is_shipped()` (`model.py:1435`) reads
`field_of(mfile, 'status')`. The intended claim — that it does not require exactly one milestone
flagged `in_progress` — is true and worth making; "reads no status field" is not.

### M2 — MAJOR — `pm init` tells every adopting consumer that U1 is running; it is not — `open`

`src/agentic_sdlc/repo/pm/skills.py:231` prints, unconditionally, at the end of the ladder:

> `check pm` U1 keeps saying so after this scrolls away, as a WARN with the count

`checks/pm.py:256` is `if 'U1' not in enabled: return`. U1 is opt-in and off by default. Measured on
the bumped consumer at stock roster: `check pm` PASS, zero U1 lines, over a tree using one of eight
declared milestone states. `pm init`'s own "Next" list, step 2, names `D9`/`D10` and `R5` as rules to
add to `checks` and omits `U1`.

This is the Appalachian Trail failure the milestone exists to prevent — a tree using three of eight
states with every gate green — reproduced by the feature built to prevent it, and made worse than
silence, because the consumer has been told the rule is watching. Either `pm init` says U1 must be
named in `[pm] checks`, or the ladder text drops the claim.

### M3 — MINOR — six of this milestone's eleven new rules are absent from the config file that documents the roster — `open`

`installables/project-devkit.toml`'s `checks` comment enumerates the opt-in set as V6, D9, D10 and
R5. `U1`, `R1`, `R2`, `R3`, `R4` and `R6` are not named anywhere in the file a consumer edits to
enable them. `pm vocabulary` lists all of them and the CHANGELOG describes them, so they are
discoverable — but not at the point of configuration. Compounds M2: the one file that would have
corrected `pm init`'s claim does not mention the rule.

### M4 — MINOR — a docstring still describes the pre-fix behaviour — `open`

`release_ledger_dir()`'s docstring (`model.py:1534`): "`order` plus `version_at` answer with exactly
one BY CONSTRUCTION". The function never consults `version_at`; `order` alone answers. Same residue
as M1, in the code this time. The behaviour is right; the sentence above it is the old model.

### M5 — MINOR — eight committed review records embed an absolute machine path — `open`

`docs/reviews/0.3.0-*.md` carry
`<agent scratchpad>` in their preamble. This
is a public MIT repo; the path leaks a machine layout and an agent session id, and it resolves to
nothing for any reader. Rule 8's "reads a path outside this checkout" in spirit. Name the probe
files; drop the directory. (This record does so.)

### M6 — MINOR — rule 8: the milestone's own records name three consuming projects — `open`

Rule 8: *"No file names a consuming project… A worked example names a shape, never a repo."*
`pm/roadmap/0.3.0-the-bump-explains-itself/milestone.md` and six `feature.md` files in this range
name "The Appalachian Trail", "NullBound" and "godot-devkit"; three `docs/reviews/0.3.0-*.md` do
too. A full sweep of the range found **`src/`, `installables/`, `tests/` and `.claude/agents/`
clean** — no consumer name, no path escaping the checkout, nothing gating on another repo's state.
So the shipped package honours rule 8; its record does not. The pattern predates this range
(`0.2.0-the-conveyor/milestone.md:110`, `CHANGELOG.md:845`), so this is an established practice
rather than a regression — but rule 8 says "no file", and either the rule carves out the PM tree or
the provenance is written as a shape.
