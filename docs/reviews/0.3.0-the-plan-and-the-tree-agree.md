## Findings

### B1 — MAJOR — `current_release` skips FORWARD past an unverifiable entry, and R5 grades the wrong release — `open`

F1's fix made an entry with anything other than exactly one claimant UNVERIFIABLE, and taught the
`version_at = "start"` loop to `continue` past it. `continue` is right when the unverifiable entry
is **behind** us — a retired milestone's row is history. It is wrong when the entry is **ahead**,
because then skipping is not a refusal to answer, it is an answer, and it is the wrong one.

```
order = [0.1.0 done, 0.2.0 DANGLING, 0.3.0 building],  pyproject.toml = 0.2.0
  current_release = '0.3.0'
  check pm exit=1
    WARN   UNBOUND: 0.2.0 is in `order` and no milestone declares version: 0.2.0
    DRIFT  pyproject.toml version '0.2.0' does not match the current release '0.3.0'
           (the milestone '0.3' claims it), which is the first unshipped entry

order = [0.1.0 done, 0.2.0 DANGLING, 0.3.0 DANGLING, 0.4.0 building]
  current_release = '0.4.0'          <- two entries skipped

order = [0.1.0 done, 0.2.0 claimed by TWO milestones, 0.3.0 building]
  current_release = '0.3.0'          <- F2's fix lands here
```

R5 then tells the consumer to move the version file from 0.2.0 to 0.3.0, skipping a release the
plan declares and nothing has shipped. `release` with no argument resolves the same 0.3.0 and would
ship it — and **R4 can never object**, because "history is a prefix" is trivially satisfied while
0.2.0 stays unshipped. The one thing the belt exists to stop is the thing the resolver walks into.

The duplicate case is the sharpest, because it is a **regression in the answer**, not just in the
reasoning. Before F2, two milestones claiming 0.2.0 gave `current = 0.2.0` with the claimant picked
by directory name — the right entry, an ambiguous owner. After F2 it gives `current = 0.3.0` — the
wrong entry. F2 traded a bad tiebreak for a silent advance of the plan.

**Two shipped verbs of this feature already disagree with the resolver over the same tree:**

```
$ pm next      0.2.0   (unclaimed)   no milestone declares version: 0.2.0
$ pm roadmap   0.1.0   0.1           shipped
               0.2.0   (unclaimed)   unverifiable
               0.3.0   0.3           building
```

`pm next` says the next release is 0.2.0 and names why it cannot be verified. `current_release`
says 0.3.0. Both ship in this feature. The honest one is the one nothing else reads.

### B2 — MAJOR — F1 is unfixed under `version_at = "ship"` — `open`

The unverifiable guard lives inside the `if cfg.version_at == VERSION_AT_START` loop. The other
branch is `shipped = [v for v in order if release_is_shipped(cfg, v)]; return shipped[-1]`, and
`release_is_shipped` returns **False** for an unverifiable entry. So a retired milestone drops out
of `shipped` and the last shipped position moves back:

```
version_at='ship'   order=[0.0.9, 0.1.0], both done
  baseline                       current='0.1.0'  ledger=0.1-m   check pm exit=0
  after retiring 0.1.0's record  current='0.0.9'  ledger=0.0.9-m check pm exit=1
    DRIFT  pyproject.toml version '0.1.0' does not match the current release '0.0.9'
           (the milestone '0.0.9' claims it), which is the last shipped entry
  0.1.0 claimed by TWO done milestones  -> identical: current='0.0.9', regression demanded
```

That is F1's transcript with the numbers changed. The previous review said F1 *"mirrors under
`version_at = "ship"`"* (line 70-71); the disposition — *"`current_release` no longer rolls backward
when a shipped milestone is retired"* — covers one branch of two. The ledger moves back with it, to
a shipped milestone's directory.

**Nothing covers this branch.** Planting *"count an unverifiable entry as shipped"* in the `ship`
branch leaves the narrow slice green (265 passed, 1 skipped — identical to baseline). Planting
`shipped[0]` instead of `shipped[-1]` **is** caught, by
`test_current_is_the_first_unshipped_at_start_and_the_last_shipped_at_ship`, so the branch has one
case and it does not reach the unverifiable interaction. `version_at = "ship"` is this repo's own
committed setting (`devkit.toml:90`).

### B3 — MAJOR — R5 reports a false reason, at exit 0, when the reason is unverifiability — `open`

When `current_release` skips its way off the end it returns None, and `_release_findings` explains
that with a fixed disjunction that never mentions the actual cause:

```
order=[0.1.0 done, 0.2.0 DANGLING]                    check pm exit=0
  WARN  R5 has no current release: every entry in `order` has shipped
        under [pm] version_at = 'start'
        ^ FALSE: 0.2.0 has not shipped. It could not be established.

order=[0.2.0], claimed by TWO 'building' milestones    check pm exit=1
  WARN  R5 has no current release: every entry in `order` has shipped
        ^ FALSE: NOTHING has shipped. Both claimants are 'building'.
```

The first is **exit 0** — a gate passing while asserting a fact about content it never established,
which is hard rule 4's first cardinal sin and the exact thing F3 was raised for. F3's fix separated
an absent plan from an unreadable **file**; it did not touch an unresolvable **position**, and the
same false-reason shape survives one layer up. `release_ledger_dir` carries the identical string
(*"every release in ... has shipped (or none has, under [pm] version_at = ...)"*), so the ledger
refuses for the same invented reason.

The vocabulary to say it correctly already exists in this feature: `pm roadmap` prints
`unverifiable` for precisely this entry.

### B4 — MINOR — R2's backlog census is fooled by a quoted-whitespace `version:` — `open`

`field_of` strips the raw line and then unquotes, so whitespace *inside* quotes survives and reads
as a non-empty version:

```
version:  (absent)        claims=[('0.1.0','0.1')]                 BACKLOG counted   exit 0
version:                  claims=[('0.1.0','0.1')]                 BACKLOG counted   exit 0
version: ""               claims=[('0.1.0','0.1')]                 BACKLOG counted   exit 0
version:      (bare)      claims=[('0.1.0','0.1')]                 BACKLOG counted   exit 0
version: "   "            claims=[..., ('   ','draft')]            NOT backlog       exit 1
version: '  '             claims=[..., ('  ','draft')]             NOT backlog       exit 1
version: "\t"             claims=[..., ('\t','draft')]             NOT backlog       exit 1
```

The three whitespace shapes drop the milestone out of R2's census and turn it into an R1
**UNSCHEDULED failure** whose message names an invisible version:

```
DRIFT  UNBOUND: milestone draft declares version:     and pm/roadmap/releases.md `order`
       does not carry it — UNSCHEDULED; `agentic-sdlc pm order --append    ` puts it on the plan
```

And the remedy the gate prescribes is one the tool refuses:

```
$ pm order --append '   '   ->  exit 2  [pm] ERROR — a version may not be empty
$ pm order --append '\t'    ->  exit 2  [pm] ERROR — a version may not be empty
```

Two definitions of "an empty version" in one package: `version_claims` uses truthiness after
unquoting, `pm order` uses a strip. The gate reddens the tree and names a fix the verb will not
perform. Story 01 criterion 3 is *"a milestone with no `version:` is backlog — a named, counted
line, never a finding"*, and this is a milestone with no version that is a finding.

### B5 — MINOR — `plan_defect` reports a BOM-damaged plan as having no frontmatter — `open`

`_FENCE` cannot match `﻿---`, so `_fence_bounds` returns None and `plan_defect` falls to:

> `has no frontmatter block — the plan is a grain, and \`order\` lives in its frontmatter`

The file **does** have a frontmatter block; a BOM is shadowing it. This is exit 1 rather than exit
0, so it is not the cardinal sin — but it is a false reason where the repo already owns the right
word: `tests/support/pm.py:44` defines `DAMAGE_FORMS = ('bom', 'blank-line', 'no-closing-fence')`
because damaged frontmatter has to be distinguishable from absent frontmatter. F3's disposition
claims the fix names *"BOM, unclosed fence, scalar `order:`, missing key, undecodable bytes"* — it
names four of the five, and BOM is the one it reports wrongly.

`pm order --append` on the same file refuses cleanly and writes nothing, which is right.

### B6 — NIT — R1 and R6 both fire on one fact, with two remedies — `open`

A `done` milestone whose version is on no plan produces two DRIFT lines:

```
DRIFT  UNBOUND: milestone 0.2 declares version: 0.2.0 and `order` does not carry it —
       UNSCHEDULED; `agentic-sdlc pm order --append 0.2.0` puts it on the plan (R1)
```

the feature record says so; this pair is not mentioned anywhere. Raised as a NIT because the output
is not wrong, only doubled — but consumers grep these lines and count them.
