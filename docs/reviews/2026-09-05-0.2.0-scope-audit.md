# 0.2.0 scope audit — the plan against the goal

**Written 2026-09-05, orchestrator pass, before any code.** The milestone was planned on
2026-09-04 as four features plus a bug and a loose design document. This is the review Chris
asked for: *are those features complete against the goal of a conveyor belt and a deterministic
SDLC?*

**Verdict: the diagnosis is right and the decomposition is wrong.** Every measurement in the
four feature files reproduces. Nothing in them is inaccurate. But three structural problems
would have made this milestone fail to close, and one deliverable the split actually depends on
is written as an escape hatch rather than as work.

Every claim below was re-derived on 2026-09-05 against the tree at `29bc4b7`. Commands are
quoted so a reader can re-run them rather than trust this file.

---

## A — Ship criterion 5 is an escape hatch, and it is the one thing the split is blocked on

The milestone's fifth ship criterion reads:

> *"The installables' middle tier is resolved, **or the milestone says in writing why it is
> not** and what blocks it."*

That "or" makes the criterion unfailable. And the thing it lets off is the thing that matters
most outside this repo: `HANDOFF.md` records that `godot-devkit` 0.25.0 **cannot green until
`agentic-sdlc` is pinnable**, and that `Makefile.devkit` — "the gate FRAMEWORK and the Godot
target ROSTER in one file" — is *"the entire middle tier and the only design problem left in
the split."*

So 0.2.0 can satisfy every criterion it sets itself and still leave the other repo blocked.
A milestone whose ship criteria can all pass while its stated purpose fails is mis-specified.

**And the problem is smaller than it was written up as.** Read against the actual file, the
split is nearly mechanical. `Makefile.devkit` is 314 lines, and the seam is visible:

| lines | what | belongs to |
|---|---|---|
| 1–146 | header, `DEVKIT_VERSION`/`DEVKIT`, `VERBOSE`, `GDK_SUM_*`, the `gdk_gate` define, `help` | **framework** |
| 147–277 | `parse` `lint` `warnings` `unit` `integration*` `scenario` `smoke` `capture` `import-cache` `uid-scan` `hermetic-scan` `hooks-self-test` `doctor` `scene` `scene-diff` `refs` `orphans` `autoloads` | **Godot roster** |
| 278–315 | `check`, `precommit`, `milestone` | **framework — but the compositions name Godot targets** |

The only genuine coupling is the last row: `precommit: check parse lint unit integration-diff`
and `milestone: check parse lint warnings unit integration-all`. Two prerequisite lists.

**The mechanism to decouple them already exists in spirit** — `[gates] extra` is precisely
"the project names targets, the framework runs them, nobody forks the file." What it does not
cover is a *language kit* contributing targets, which is a third party neither the framework
nor the project.

**Recommended resolution — `-include` plus two variables, not a third TOML key:**

```make
GDK_TIERS_MK        ?= Makefile.tiers
GDK_PRECOMMIT_TIERS ?=
GDK_MILESTONE_TIERS ?=
-include $(GDK_TIERS_MK)

precommit: check $(GDK_PRECOMMIT_TIERS)
milestone: check $(GDK_MILESTONE_TIERS)
```

`godot-devkit`'s `install-runners` writes `Makefile.tiers`: it *defines* `parse`/`lint`/`unit`/…
and *sets* the two variables. Three reasons this beats a `[gates] precommit` config key:

1. **Make cannot get target definitions out of TOML.** The tier file has to exist regardless, so
   a file that both defines the targets and declares where they run is ONE source of truth; a
   TOML key would be a second one that can disagree with it.
2. **No sub-make and no runtime cost.** `-include` resolves at parse time; prerequisites stay
   prerequisites. The `check` target's sub-make dance exists because `[gates] extra` is genuinely
   per-project data; tiers are not.
3. **`[gates] extra` stays exactly what it is** — the *project's* gates — instead of becoming a
   place where three different authorities write into one list.

**This is promoted to a feature of its own and ship criterion 5 loses its "or".**

## B — The plan contradicts itself about what to build first

`design-the-three-belts.md` § *What is NOT yet designed*:

> *"Which command is 'narrow' is per-project, and nothing declares it. … **This is the first
> thing to solve**, because it is what every other layer's economics rest on."*

`the-release-is-a-conveyor` § *The first slice, and why it is that one*:

> *"**`review-landed` then `gate`, in that order**, with the disposition check."*

Both arguments are good and they name different work. The design document is right about
leverage: `release` runs weekly, the story belt runs continuously, and the measured 170× is in
the story belt. The feature file is right about cheapness: `verdict.parse` already returns
dispositions, so `review-landed` is nearly free.

They are not actually in conflict once the XL feature is split — they are two features, and the
story belt is the one with the larger payoff. **Both ship; the story belt is planned as its own
feature so it cannot be starved by the conveyor's tail.**

## C — `the-release-is-a-conveyor` is XL and carries four unrelated deliverables

`size: xl`, `risk: high`, and reading it there are four distinct things inside:

1. the `release` step machine + `[release] steps` + on-disk run state + skip-to-ledger,
2. `install-sdlc`, which generates the SDLC doc from the step list,
3. the `adopt` step list, which is a different operation with different postconditions,
4. the `change` pair — which the design document then supersedes and renames the story belt.

An XL feature with four deliverables is a feature that reports "still building" at close. Item 4
already belongs to B. Items 1+2 are one thing (a step machine is not deterministic if its
documentation is hand-written — that is the feature's own risk 2). Item 3 shares the driver and
nothing else.

**Split into: the conveyor driver + generated docs (1+2), and `adopt` (3).**

## D — Nothing in the plan says the conveyor gets used on this milestone

The whole argument for the release conveyor is that prose gets followed incorrectly — three
times, documented. The plan builds the machine and then leaves 0.2.0's own release to be
performed by an operator reading `SKILL.md`.

**A conveyor whose first release is done by hand has not been tested.** Ship criterion added:
0.2.0 is released *through* `agentic-sdlc release 0.2.0`, and any step that had to be skipped is
in the ledger with a reason. That is the same self-hosting bar `install-hooks` already meets and
it is the only honest proof the driver works.

## E — Two features collide on `KNOWN_GATES`, and both are `phase: 1`

`the-extraction-finishes` **prunes** the roster (eight phantom names out).
`the-kit-owns-the-gates-that-scan-its-own-artifacts` **grows** it (four gates in).

Both carry `phase: 1`, `depends_on: []`. Run in parallel on disjoint file sets — which is what
§2 of `SDLC.md` dispatches — they collide on `src/agentic_sdlc/cli.py`, and the census test the
first one ships is the thing the second one has to update. Serialize: prune, prove
`roster == dispatchable`, then grow through the proven census.

The `consumed_by` edges are also asymmetric today —
`the-kit-owns-…` declares `consumed_by: ["0.2.0/every-gate-reports-its-cost"]` while that
feature declares `depends_on: []`. `pm validate` passes because it resolves refs rather than
requiring symmetry, so this is a plan defect the gate cannot see.

**F3 — the deprecation window is still open here.** `model.py:89` `DEPRECATED_STATES`,
`model.py:112` `deprecated_write`, three `_refuse_deprecated` call sites in `pm/cli.py`
(334, 605, 622), the census in `checks/pm.py` (152, 196–240), and window assertions across
`tests/test_pm_gate.py` and `tests/test_pm_verbs.py`. This repo's own tree holds **zero**
retired words, so trimming reddens nothing here.

The bug file says to edit `src/godot_devkit/repo/pm/model.py`. That path does not exist; it is
`src/agentic_sdlc/repo/pm/model.py`. Every step in the bug is otherwise correct.

**F4 — the cost funnel is where the feature says it is.** `Makefile.devkit:112` `define
gdk_gate` wraps `gdk_gate_capture` (114–115) and `gdk_gate_verdict` (123), with the command's
own exit preserved through `$GDK_GATE_EXIT`. Every gate target in that file routes through it
except `runners-self-test`, which open-codes the same three calls (180–196), and the four
runners that publish their own verdict (`parse`, `lint`, `warnings`, `unit`).

**So "instrument the funnel" covers most gates and misses `runners-self-test` and those four.**
The feature does not say this. `gdk_gate` is the common CALLER, not the funnel.

**Corrected 2026-09-05, after the phase-3 PO traced the call sites — `gdk_gate_verdict` alone is
not the funnel either.** It is called **6× in `parse.sh`**, 5× in `warnings.sh` and 7× in
`unit.sh` (some are alternative exits, so the per-run count is ≤6, not always 6 — but >1 is
reachable), and `unit.sh:343` publishes through `gdk_gate_publish` and never calls
`gdk_gate_capture` at all. Instrumenting `gdk_gate_verdict` naively files up to six rows for one
gate run, and misses `unit` entirely.

**The funnel is the PAIR, keyed on the log slot: `gdk_gate_log` opens it, `gdk_gate_verdict`
closes it, one row per slot per run.** That is the shape `0.2.0/every-gate-reports-its-cost`
story 02 builds to. Two consequences the feature file names neither of:

- a *sourced* shell library has no access to `DEVKIT`, which is a make variable, so
  `Makefile.devkit` grows one `export GDK_LEDGER_CMD ?= $(DEVKIT)` line — **which collides with
  `the-middle-tier-splits`, and is why phase 2 lands before phase 3**;
- `gdk_gate_verdict <TAG> <message> <log>` has no census argument and the census lives inside
  prose. **Do not regex it out of the message** — that is how a run over 683 files files
  `census: 0`, which is a lie with a number on it. It arrives as `GDK_GATE_CENSUS`.

## The ruling the plan asked for, twice

`the-extraction-finishes` and `milestone.md` both defer the same question. It has one answer
and it settles `Makefile.devkit`, `doctor.sh`, `ci-verify.yml` and `cc-godot-sandbox.sh`
together:

> **An installable belongs to the kit whose ARTIFACT it acts on — not to the kit whose
> STRUCTURE it borrows.**

Applied:

- `cc-godot-sandbox.sh` guards Godot engine boots. **It goes to `godot-devkit`.** So does
  `Makefile.devkit`'s `hooks-self-test` target, which exists only to replay its corpus.
- What stays here is `check hooks` (already shipped, already passing) plus the self-test replay
  over the hooks *this* kit installs — `cc-commit-pathspec.sh`, `cc-stop-gate.sh`,
  `cc-write-confine.sh`, and the two ledger couriers.
- `Makefile.devkit`, `doctor.sh`, `ci-verify.yml`: the structure is ours, the roster is not.
  Framework stays, roster leaves through the `-include` seam in A.
- `model.py`'s D8 `version_file = 'project.godot'` default is a **Godot default in the agentic
  kit** and changes to `pyproject.toml`, which is what this package actually versions from. It
  is configurable, so this is a default fix, not a behavior change — but a stock consumer that
  is not a Godot project currently gets a D8 pointed at a file it does not have.

## Ship criteria, restated so each can fail

1. A `git init` repo with no `devkit.toml` runs `agentic-sdlc check all` and exits 0 or 1 —
   never 2 — and a test asserts `roster == dispatchable`.
2. `Makefile.devkit` names no Godot target, and a gate asserts it.
3. `release` and `adopt` both run as step lists that refuse to advance; a skip is a ledger row
   with a reason.
4. The SDLC document a consumer reads is generated from its own step list.
5. Every gate records name, duration, verdict and census through one funnel, failing open, and
   `pm ledger report` grows the view that answers *what got slower*.
6. The four gates that scan this kit's own artifacts ship in `[checks] all`.
7. `verify --changed` answers *what proves this edit* from config, names any path that matched
   nothing, and falls back to wide.
8. **0.2.0 is released through `agentic-sdlc release 0.2.0`.**

## H — found while executing, not while planning

**H1 — a builder's `git stash` stashes every other builder's work.** `SDLC.md` §2 dispatches
builders in parallel on disjoint FILE sets, which is the right unit for edits and the wrong one
for git: `git stash`, `git checkout -- .`, `git restore` and `git reset` act on the whole
worktree regardless of whose files are in it. Measured 2026-09-05 with seven builders running:
one stashed to watch a test fail at HEAD — exactly the discipline §2 asks for — and took six
peers' uncommitted work with it, including staged deletions. It popped cleanly and nothing was
lost.

Two things follow, and only the first landed in 0.2.0:

- `SDLC.md` §2's builder list now forbids repo-wide git commands and names the two safe ways to
  watch a test fail. That is prose, and prose is what this milestone exists to replace.
- **The structural fix is a worktree per builder**, and `tools/dev/agent-worktree.sh` already
  exists to make one. Nothing in the dispatch loop uses it. That is a finding against the SDLC
  itself rather than against this milestone's scope — filed here so the next milestone has the
  measurement rather than re-deriving it from a worse incident.

**H2 — a concurrently-edited `devkit.toml` reddens the suite for reasons that are not the code.**
`tests/test_pm_gate.py::EveryConfigSection` reads the repo's own config, so a builder mid-write of
`devkit.toml` produced five SUBFAILs in an orchestrator run and passed on re-run two minutes
later. Self-hosting is what makes this package's gates honest and it is also what couples the
suite to the working tree. Not a defect; a thing to know before believing a red run taken while
builders are live.

**H3 — the telemetry shipped and this session recorded zero dispatch rows.**
`pm ledger report 0.2.0` says `0 dispatch row(s)` after thirteen builder dispatches. The two
ledger couriers are installed, armed and registered in this repo's `.claude/settings.json`, and
their corpora pass. They never fired because **the orchestrating session's project root is the
parent directory**, not this repo — Claude Code reads `.claude/settings.json` from the root it
started at, and the `cd` a tool call makes afterwards does not change that.

Nothing is broken. But it is the feature's own thesis pointed back at it: *a guard nobody wired
is not there*, one level up from the hooks it was written about — a courier registered in a file
the session never read is a courier that records nothing, and the only reason we know is that a
report printed a zero instead of a number.

Two consequences worth carrying forward, neither in 0.2.0's scope:

- **`verify --plan`'s ratio has only `gate` rows to work with here**, so the narrow-vs-wide
  numbers it prints on this tree are gate costs and not dispatch costs. The 170x that motivated
  the whole story belt is still a hand measurement.
- **`check hooks` reports the corpus is armed, which it is.** It has no way to know whether the
  SESSION registered it, and that is a different question with a different owner. Whether this
  package should be able to ask it at all is a 0.3.0 question.
