# 0.3.0 plan review — the engine has no opinion

**Reviewed 2026-09-05 on `milestone/0.2.0-the-conveyor`. This is a review of a PLAN, not code.**
Lens: CLAUDE.md hard rule 9 — *express, never infer* — and nothing else. Not a bug hunt.

Reviewed: `CLAUDE.md` rules 5 and 9, `docs/design/state-categories.md` (whole),
`pm/roadmap/0.3.0-the-engine-has-no-opinion/` (milestone + both features),
`.claude/rules/pm-execution.md`, and enough of `src/agentic_sdlc/repo/pm/` and
`repo/conveyor/` to check the §6 census against the code it cites.

**The design is right.** Categories-not-words is the correct answer, the `obe`-is-`done` ruling is
correct and well-argued, and report-never-refuse restores a rule the repo already had. Everything
below is about whether the PLAN is buildable as written. Two things say it is not yet: the
milestone and its own feature state opposite ship criteria, and the census the milestone sizes
itself from is both mis-cited and short.

---

## P1 — BLOCKER. The milestone and its feature contradict each other on the fallback

`milestone.md` ship criterion 5:

> *"The shipped default maps exactly 0.2.0's `LIFECYCLE`, so a consumer declaring nothing sees no
> behaviour change — rule 5, and the only way this lands without reddening every tree."*

`features/states-are-categories-not-words/feature.md` ship criterion 5:

> *"`init` writes the states and the transitions into `devkit.toml`, and the runtime reads them
> every run with no fallback. **A tree missing the section gets a refusal that prints the seed to
> paste.**"*

A consumer declaring nothing either sees no behaviour change or is refused by name. It cannot be
both. The design document carries the same contradiction inside one section: §4 line 156 says *"a
consumer that declares nothing sees no change"* and §4 line 184 says the reader *"does not fall
back."*

This is not a wording slip — it is the one ruling the milestone has not actually made, and it is
load-bearing on rule 5's split, on the bump story, and on whether `adopt`'s `config-updated` is a
convenience or the only way a consumer survives the pin.

The code makes it sharper than the documents do:

- `src/agentic_sdlc/repo/installables/project-devkit.toml` has **zero uncommented lines** — the
  seed `init` writes is entirely commentary. If 0.3.0 keeps that convention, `init` materializes
  nothing and a freshly-initialized project is refused on its first `pm` call. Materializing the
  table means changing the seed's whole commenting convention, which no grain names.
- `src/agentic_sdlc/repo/init.py:158-193` — `_write_seed` **never overwrites an existing
  `devkit.toml`**, and `--force` is documented as not touching it *ever* (`init.py:30-32`). Every
  existing consumer already has one. So on the 0.3.0 bump, no-fallback means every existing tree
  is refused until a human hand-pastes a section, and `init` is structurally unable to help.

The plan gestures at this with `adopt`'s `config-updated`, but `adopt` is a verb a consumer has to
choose to run; rule 8 says this package knows nothing about whether they will.

**Argued on rule 9, no-fallback is the right answer** — a default nobody can see is the engine's
opinion wearing the project's clothes, exactly as the design says. The fix is not to soften it. It
is to (a) delete milestone criterion 5's "no behaviour change" clause and replace it with the
migration that actually happens, and (b) add the grain that makes `init` able to ADD a missing
section to an existing `devkit.toml` — an append, in the shape `_write_gitignore` already uses at
`init.py:207-247`, which appends missing entries and never rewrites. That grain does not exist in
0.3.0 and the milestone cannot ship without it.

## P3 — MAJOR. The census is short, and the biggest omission is a written data format

Everything below was found by grepping `src/agentic_sdlc` for state literals and reading the
callers. **Most of it is READING, and saying so is the point** — the census is not seven items long
because there are only seven; it is seven long because nobody swept.

### DECIDING — not in the census

**1. The ledger's dispatch snapshot buckets. `src/agentic_sdlc/repo/pm/cli.py:1524-1557`.**
This is the one that should worry the milestone, and its own docstring convicts it:

> *"The bucket KEYS are frozen and the states they match follow the vocabulary. `stories_wip`
> collects stories at `building` and `features_review` features at `reviewing` … **A project with
> a genuinely renamed vocabulary records empty lists**, which is a true statement about a tree
> whose states this row shape cannot name."*

The engine has decided which states are worth recording on a ledger row, by name
(`cli.py:1543-1556` reads `model.BUILDING` and `model.REVIEWING` four times), and a project that
renames its words gets silently empty attribution. That is precisely the failure mode §1 uses to
justify the whole milestone, applied to a surface the milestone never names.

It is also the **hardest** thing in 0.3.0 and the plan treats it as absent. Ship criterion 6 says
only *"`pm ledger report`'s dwell columns are per CATEGORY."* Dwell columns are a rendering change.
The dispatch buckets are **keys inside JSONL rows already written to every consumer's
`ledger.jsonl`**, consumed downstream by `report.py:104-112` `DISPATCH_BUCKETS` for grain
attribution. Changing them is a data migration with a back-compat story; keeping them is keeping a
hardcoded state opinion through the milestone that exists to remove hardcoded state opinions. The
docstring already argues for keeping them. **The plan must pick, in writing, and it does not know
the question exists.**

**2. `execlist._phase_key`, `src/agentic_sdlc/repo/pm/execlist.py:44-50`.** Sorts phases
`digit < 'seam' < everything else`. `seam` is a word the engine knows about a project's phase
vocabulary, in exactly the way `building` is a word it knows about a project's state vocabulary.
Small, real, unlisted. (`cli.py:874-880` spells `'seam'` and `'unphased'` the same way.)

### READING — checked, and clean

- **`pm new` scaffolding** (`repo/pm/templates/`, `cli.py` new paths) — renders a template with an
  id and a parent. It picks no status and asserts no order. **READING.**
- **`pm status` grouping** (`cli.py:865-885`) — groups by the `phase:` field the grain declares and
  prints them in declared order. **READING.** (Its `n_done` tally is a by-name ask; see P9.)
- **`pm sync` / `execlist.sync`** (`cli.py:1014-1043`, `execlist.py:71-198`) — renders the order a
  milestone and feature already declare via `phase:` and `depends_on:`, and `_toposort` degrades a
  cycle to name order rather than choosing a resolution, leaving the finding to V5. **READING**,
  and a good example of the boundary held correctly.
- **`report.py` bucketing** (`report.py:88-112`) — renders what the ledger rows hold. The opinion
  is upstream in the row shape (item 1), not here. **READING.**
- **The conveyor's step-kind dispatch** (`driver.py:177-199`, `steps.py:186-199`) — `AUTOMATIC` /
  `GATE` / `JUDGEMENT` are a table of what a step CAN do, with `steps.py:232-237` refusing a step
  whose kind and callables disagree. The comment *"a step whose behaviour needs a fourth kind is a
  fourth kind, not an `if name ==`"* is the rule-9 discipline stated in code. **READING.**
- **`verdict.py` disposition semantics** (`verdict.py:105-160, 362-400`) — parses four disposition
  kinds and carries `disposition_value` RAW, docstringed *"(D5 — no inference)"*. It refuses
  malformed input and interprets nothing. **READING**, and the cleanest surface in the package.
- **`install-sdlc` rendering choices** (`repo/install.py`, `init.py`) — writes whole files or
  refuses by path, and leaves project-owned files alone on collision. **READING.**
- **`checks/pm.py:129-134`** — the `D5 cannot place 'building' in …` NOTE. The engine reporting its
  own blindness rather than guessing. **READING**, and the model for what the rest should do.
- **`checks/grain_shape.py:167-186` `_kind_of`** — census item 7, and the census's own verdict
  ("already half-declared") is right: doc names come from `model.*` constants, slot names
  (`'stories'`, `'bugs'`, lines 182-185) are bare literals. **READING** from a half-declared
  convention. Lowest-value item in the census; it is a naming cleanup, not an opinion removal.

## P5 — MAJOR. Scope. Two features is not honest

The feature's "How each conveyor step is encoded" table has 16 rows. The registry has **40 steps**
across four belts (`steps.py:2048-2135, 2314-2317`): release 21, adopt 8, story 5, feature 6. The
table shows 5 of the release belt's 21 and **none of adopt's 8**.

For feature 1 that omission is harmless — only 8 steps write a status, and the table names all 8
correctly. For **feature 2 it is the whole scope**, because the omitted steps are exactly the ones

edge table says "red gate → REPORT, and proceed", which means `agentic-sdlc release` will walk past
a failing test suite to `tag`. That may well be right — `check` is the gate, the belt is not — but
it is the single most consequential consequence of this milestone and it appears nowhere except as
one row in a two-column table.

Feature 2 is sized `m` and labelled *"mostly subtraction"*. Deleting `Answer.no`/`UNVERIFIABLE`
halting (`driver.py:139-174, 323-390`) is subtraction. Re-ruling 14 halting steps, keeping the
0.24.0 ordering lesson alive without the halt, and writing the test that holds the input/tree line
(its own criterion 3, called *"the thing that will erode"*) is not.

Add P1's `init`-append grain, P3's ledger-row ruling, and P4's D6/D8/D9/D10 question, and **0.3.0 is
four or five features, not two.** This is 0.2.0's failure mode — `docs/reviews/2026-09-05-0.2.0-scope-audit.md`
exists because a milestone's real size was hidden until it was being built — recurring one milestone
later, and the milestone document's own risk list does not name it.

## P6 — SHOULD-FIX. The transitions table: argued both ways, and it lands legitimate-with-a-caveat

**Against.** `[pm.transitions.feature] feature-reviewing = "reviewing"` has a **key set the project
cannot change**. The keys are the engine's step names, shipped in `steps.py`. So the engine knows
there is a thing called "the review has started" and a thing called "the work is finished", for
every grain kind, and asks the project only to name its word for each. That is structurally
identical to the opinion being removed: 0.2.0's sin was *"`[pm] story_states` is configurable and
every question is asked BY NAME"*; this is *"`[pm.transitions]` is configurable and every step is
named BY THE ENGINE."* The lattice moved up a level from words to steps and the engine still holds
it. The feature's own risk 1 half-sees this — *"a transitions table is a second place a state name
is written"* — but frames it as a drift surface, which is the smaller problem.

**For.** `steps.py:73-92` shows the step list is **already** project-configurable: `[release] steps
= [...]`, `[adopt]`, `[story]`, `[feature]`, each defaulting to a `DEFAULT_*_STEPS` tuple. A project
selects and orders its own belt. The step registry is a published vocabulary the project draws
from, the same way `[pm] checks` names D-ids and `pm vocabulary` exists to print exactly this kind
of closed set at a pin bump. Naming a step is not deciding what a move means. And the feature's
"ASK BY CATEGORY, WRITE BY NAME" argument is correct and load-bearing: a category holds several
states, so writing by category would make the engine guess a member — strictly worse.

**Where I land: legitimate, and the plan has not earned it yet.** Selecting from a closed menu is
not the same as declaring your own flow — a project cannot invent a step, so `[pm.transitions]`'s
key set is the engine's, full stop. That is fine, but it must be *said*, and the feature currently
implies the opposite by presenting the table as pure project declaration. One paragraph fixes it:
**the step registry is this package's published API surface, versioned like the CLI, read at a pin
bump through `pm vocabulary` — which under this milestone must start printing transitions.** Say
that and the table is the project declaring its flow over a vocabulary the engine publishes, which
is exactly the Jira shape the design argues for. Leave it unsaid and it is the engine's opinion
with a config file in front of it.

(`pm vocabulary`'s docstring at `cli.py:1061-1062` currently reads *"There are no TRANSITIONS to
print."* That line is falsified by this milestone and no grain names it. See P8.)

## P7 — SHOULD-FIX. "Three categories, hard" survives rule 9 — and costs D5 resolution nobody priced

Tested rather than assumed, as asked.

**It survives, and the reason is that it is not the same KIND of opinion.** Rule 9's edge is *"is
this reading what the project declared, or deciding what the project should do?"* Three categories
is neither. `BUILDING = 'building'` is a **value** the engine asserts about the project's
vocabulary — a project contradicts it by renaming a word, and then the gate silently stops asking.
`todo | in_progress | done` is the **domain** the project's own mapping is a function into — a
project satisfies it by mapping, and can never contradict it. Rule 9 already licenses exactly this:
*"a config value of the wrong shape: exit 2, always."* A category set is the type of the `states`
key. Refusing a state mapped to none or to two is the engine reading a malformed declaration, which
rule 9 names as the one thing it is always allowed to do.

The operational test confirms it: after 0.3.0, no engine question ever compares a category against
a project's word. Every question is `category_of(status)`, and `category_of` is a lookup in the
project's own table. The engine's opinion never touches the project's vocabulary.

**The unpriced cost.** D5 today is `states.index(status) >= states.index(BUILDING)`
(`model.py:1084`) — resolution 7 within `LIFECYCLE`. After 0.3.0, D5 is *child's category > parent's
category* — **resolution 3**. A story at `packaging` under a feature at `building` are both
`in_progress`, and D5 goes silent where today it reports. Same for D2, whose
`STALLED_IF_ALL_STORIES_DONE` is today `LIFECYCLE[:index('reviewing')]` — three states — and becomes
"parent in `todo`" — two.

That is a real reduction in what the gate can see, and it is the direct price of the hard opinion.
It may be the right price: within-category order is presentation, and a gate keying on it makes the
words load-bearing again (milestone risk 3 says so). But **the milestone lists the resolution loss
nowhere**, and the design's §4 sells the change as pure gain ("that deletes `model.py:1030`'s
index comparison"). A reader of these documents cannot tell that D2 and D5 will report strictly
less. Write it down, and confirm it is accepted — rule 4's read-side sin is a gate that misses real
drift, and this narrows two rules' vision on purpose.

## Note on the verdict vocabulary — itself a finding

`src/agentic_sdlc/repo/pm/verdict.py:72-79` — `VERDICTS` is six words:

```
SHIP · SHIP-WITH-FIXES · HOLD · RELEASE-SAFE · RELEASE-WITH-FIXES · NOT-RELEASE-SAFE
```

The docstring at `:68-71` says *"Six, because a release review and a feature review answer
different questions with the same three shapes."* **A PLAN review is a third question and the
vocabulary does not cover it.** `PLAN-SOUND` / `PLAN-SOUND-WITH-FIXES` / `PLAN-NOT-SOUND` are not
in the tuple, so `verdict.parse` would refuse this record with them
(`verdict.py:407-409`). I use `SHIP-WITH-FIXES` below, which is the feature-review shape and the
closest honest fit — a design review of a milestone that has not been built.

Recommend a fourth pair in `VERDICTS`. This is a live gap, not hypothetical: 0.3.0's own
`states-are-categories-not-words` is `risk: high, size: l` and will be plan-reviewed again before
it is built.

## Verdict

**`SHIP-WITH-FIXES`** — vocabulary limitation noted above; read it as *plan sound with fixes*.
