# Review — 0.4.0/every-move-breadcrumbs-the-next-step

One feature, one story (`st-a-move-prints-what-the-conveyor-asks-next`), built in `d0db6c4`
alongside `every-grain-is-on-a-stopwatch`; only the breadcrumb half is graded here. Read at tree
state `318bac1`, against `HEAD:src/agentic_sdlc/repo/pm/cli.py` because the working copy of that
file is +35 lines under another agent's hand. Reviewed cold against the feature file, the story
including its close block, `CLAUDE.md` hard rules 3/4/5/6/9/10/11, `SDLC.md` §0 and §6, and the
shipped `reviewer` contract. Refs tool: raw `grep` — this repo ships no reference-aware search —
plus two live read-only CLI probes.

**Verdict: SHIP-WITH-FIXES.** The thesis holds and the design is the right one: a status write now
says what the conveyor asks next, the sentence is assembled at runtime rather than templated, the
kill switch is one key with a stock-ON default that a test pins, and STDOUT under `pm` is
byte-identical — the amended quartet case proves that, not prose. What is wrong is that the one
word in the line that is *not* derived is the argument shape (`<id>`, where both belts print
something else in their own `--help`), the check list is read from the shipped REGISTRY rather than
from the belt's declared, ordered step list, and the line the changeset promised would never touch
STDOUT reaches it on every belt run.

The breadcrumb's own output was derived by reading, not captured: `_breadcrumb` composes

## Blockers

- **`M1` MAJOR `src/agentic_sdlc/repo/pm/cli.py:315`** — the breadcrumb reads
  `steps.registry_for(belt)`, the shipped registry, where the belt itself runs
  `driver.step_names(operation)` (`driver.py:155-162`, called at `driver.py:558`), which is
  `steps.steps_for` over `[<op>] steps` — *"the ordered check list … never a quietly shorter belt"*.
  Two consequences, one of which bites in this tree today. **(a) Wrong order, stock config.**
  `FEATURE_STEPS` is declared `stories-done, review-recorded, findings-landed, feature-verified`
  (`steps.py:1329-1334`); `DEFAULT_FEATURE_STEPS`, what the belt runs, is `stories-done,
  feature-verified, review-recorded, findings-landed` (`steps.py:64-69`). So
  `pm feature building <id>` prints the four names in an order `close feature` will not run them —
  and every other surface that names them prints the run order: `docs/sdlc-protocol.md:96-99`,
  `CHANGELOG.md:170-171`, and the function's own docstring at `cli.py:296`. The breadcrumb is the
  only place in the package that says `review-recorded` before `feature-verified`. **(b) Wrong set,
  configured consumer.** A project declaring `[feature] steps = ["stories-done"]` gets a breadcrumb
  naming four checks, three of which its belt will never ask. That is the engine restating its own
  registry instead of reading what the project declared — hard rule 9's edge exactly, and rule 5's
  *"per-project variation is the consumer's `devkit.toml`"*. The story's AC1 says both *"the checks
  it will run"* and *"read at runtime from `registry_for`"*; where the criterion contradicts itself,
  the belt is the authority. Fix: `driver.step_names(belt)`, guarded — a `ConfigError` from a bad
  `[<op>] steps` must fall through to silence, never to the registry, because a status write must
  not start exiting 2 over a belt's config.
- **`M2` MAJOR `src/agentic_sdlc/repo/pm/cli.py:318-319`** — the subject placeholder is the literal
  string `<id>`, hardcoded, in the one sentence this whole feature exists to have someone copy.
  `driver.SUBJECT` (`driver.py:38-43`) is the runtime source of each belt's subject shape and is
  what the belts' own `--help` renders: probed above, `close feature <milestone>/<feature>` and
  `release <version>`. So the line printed when a feature reaches `done` is
  `` `agentic-sdlc release <id>` `` — and `release` takes a **version**, never a grain id;
  `ms-0.4.0` is refused by `version_defect` through `subject_defect` (`driver.py:370-376`). The same
  line after a story's `done` says `` `close feature <id>` `` where the belt wants two
  slash-separated segments. Every check name in the sentence is derived and the one placeholder is
  not, which is the failure mode the feature's own rule-9 section was written to prevent. Fix:
  `driver.SUBJECT[belt][2]`.
- **`M3` MAJOR `src/agentic_sdlc/repo/pm/cli.py:319-320` with `driver.py:421-424,242`** — the
  breadcrumb reaches the belts' STDOUT, and the changeset ships a promise that it does not.
  `driver._writer` performs the belt's one write by calling `pm_cli.main` in process with
  **stdout and stderr redirected into the same buffer** (`driver.py:421-422`), flattens the buffer
  to one string (`:424`), and the driver prints it as `[<op>] write: <said>` on stdout
  (`driver.py:242`). So `close story` (story → `done` → `ABOVE['story']`) and `close feature`
  (feature → `done` → `ABOVE['feature']`) now emit the breadcrumb inline, on stdout, inside a belt
  line — where it is not a separate line at all, and where it sits a few lines above the belt's own
  `next:` after-list, giving one command two next-step statements, one of which carries `M2`'s wrong
  argument shape. `CHANGELOG.md:174-175` states *"**STDOUT is byte-identical** — the status line is
  still the one line a consumer parses"*, and story AC5 says the breadcrumb *"is an additional
  line"*. Both are true of `pm` and false of the three belts, which are the paths consumers put in
  Makefiles and hooks (rule 6: output line shapes are contract). Nothing caught it because no case
  asserts the content of `[<op>] write:`. Fix: either suppress the breadcrumb when the write comes
  through `_writer` (the belt already teaches the next rung itself), or stop merging stderr into
  `said`; then the CHANGELOG sentence becomes true rather than aspirational.

## Findings

- **`N1` MINOR `tests/test_pm_verbs.py:107-131`** — the case covers two of the six kind x category
  combinations the breadcrumb has: `feature -> in_progress` (`CLOSES['feature']`) and
  `story -> done` (`ABOVE['story']`), plus the milestone-`done`-says-nothing negative.
  `CLOSES['story']`, `CLOSES['milestone']` and `ABOVE['feature']` are asserted nowhere in the suite
  — and `ABOVE['feature']` is the literal text of AC2 (*"a feature's [close points] at `release`"*).
  Mutating `ABOVE = {'story': 'feature', 'feature': 'story'}` at `cli.py:284` leaves every case
  green. It is also the untested half that carries `M2`'s `release <id>`. The story's proof row
  claims the status-move quartet *"already asserts what a write prints for all four kinds"* and is
  amended *"rows, not a new family"*; in fact a new function was added and it never touches `bug`.
  Fix: parametrize the existing case over `(kind, to, expected_verb)` rather than adding another.
- **`N2` MINOR `tests/test_pm_verbs.py:133-148` against `src/agentic_sdlc/repo/pm/cli.py:309`** —
  the feature's ship criterion says *"A test asserts every breadcrumb is reachable from
  `registry_for` **or from `[pm.states.*]`**, so a hardcoded next-step cannot be added without
  failing."* Only the `registry_for` half is asserted. Every breadcrumb case builds a stock tree, so
  replacing `model.flow_of(cfg, kind).category(to)` with a literal
  `{'building': IN_PROGRESS, 'done': DONE_CATEGORY}` map — precisely the hardcoded opinion about
  state words that rule 9 forbids and that AC3 claims is unaddable — passes the whole suite. Note
  that the printed line contains **no state word at all**, so AC3's *"a project declaring different
  state words gets its own words back"* can only mean *responds to* its own words; that is a real
  property and it has no case. `tests/support/pm.declaring` is the harness a row would use.
- **`N3` MINOR `README.md:176-190`** — the `[pm]` block a reader browses to learn the pm config keys
  lists `roadmap_dir`, `template_dir`, `review_dir`, `story_ordinal_prefix`, `checks`, `version_*`
  and does not list `breadcrumbs`. The seeded consumer config does carry it
  (`installables/project-devkit.toml:117-120`), and `test_config_seed.py`'s commented-default guard
  binds its value to `model.py:295`, so the capability is discoverable where a consumer edits — this
  is the second surface, not the only one. A DELTA for the tech-writer.

## Nits — recorded and carried

- **`T1` NIT `src/agentic_sdlc/repo/pm/cli.py:309`** — open-codes `model.flow_of(cfg, kind).category(to)`
  where `model.category_of(cfg, kind, to)` (`model.py:510-514`) is the named reader, used two
  functions away at `cli.py:649` for the same question.
- **`T2` NIT `src/agentic_sdlc/repo/pm/cli.py:318`** — re-derives the belt's spoken verb as
  `'close ' + belt`. `driver.CLOSE_VERB` (`driver.py:28`) and `driver._spoken` (`driver.py:308-311`,
  docstring *"How this operation is INVOKED, which is not always its name"*) already own that
  mapping. Same class as `M2`, one severity down because the string is right today.
- **`T3` NIT `src/agentic_sdlc/repo/pm/cli.py:500,505`** — `_breadcrumb(cfg, 'bug', to)` is called on
  both bug paths, and neither `CLOSES` nor `ABOVE` holds a `bug` key, so every bug move pays a
  `flow_of` lookup and prints nothing. Correct — no belt closes a bug — but unlike the milestone
  case at `cli.py:281-283` it carries no comment saying so, and no case pins the silence, so the
  feature file's *"Every `pm <kind> <status> <id>` write prints"* is untrue for one whole kind with
  nothing recording that it is deliberate.
- **`T4` NIT `src/agentic_sdlc/repo/pm/cli.py:319-320`** — the status line goes to stdout and the
  breadcrumb to stderr with no flush between. With stdout block-buffered (piped) and stderr not,
  `pm story done <id> 2>&1 | cat` can print the breadcrumb **before** the status line it is supposed
  to follow. Cosmetic; a `sys.stdout.flush()` before the print settles it.

## Rule check

- **Rule 9 — the one this feature lives closest to.** The design is right and the discipline is
  visible: no sentence in the output tells anyone what they *should* do, the category comes from
  `[pm.states.<kind>]` and the check names from the registry, and the milestone-`done` case
  deliberately says nothing rather than inventing a step. Two words escaped the discipline —
  the check list is read from the wrong reader (`M1`) and the argument shape from no reader at all
  (`M2`) — and the guard that was supposed to make an escape impossible watches one of the two
  sources (`N2`).
- **Rule 4.** No gate was touched and nothing new writes; `_breadcrumb` returns `None` and is called
  strictly after `_set_status`/`_stamp_status` on every path. The nearest thing to a sin is `M1`(a):
  a line that names a real belt and misstates its order, in a tree where three other surfaces state
  it correctly.
- **Rule 6.** A new line on every status write plus a new config key is a minor bump; 0.4.0 is one,
  `CHANGELOG.md:168-176` carries it, and the version sites are untouched (bump-at-close, D8 off).
  The unclaimed part of the bump is `M3` — the belts' stdout changed too.
- **Rule 11.** The capability advertises itself in the strongest possible surface: it prints. The
  off switch is in the config a consumer actually edits, bound to the code default by
  `test_config_seed.py`. `README.md` is the gap (`N3`), and `pm --help` says nothing about the
  breadcrumb or the key — not raised, because the line itself is the discovery surface.
- **Rules 1, 2, 3, 10.** Stdlib only; the `steps` import is function-local (a cycle break, `steps`
  imports `driver`) and boots nothing; no write behaviour changed and the no-op path breadcrumbs
  exactly like the write path, so idempotence is unaffected; the four cases are the cheapest tier
  that can fail.
