## The five things I was asked to attack

**1. Is `GDK_LEDGER_GRAIN` the right source?** The transport is right and the reasoning in D2 is
right — a fourth `env_arg` beats a second mechanism, and the value is copied rather than derived.
The *source* is half-built: nothing writes it, nothing documents writing it, and it is the only
`GDK_LEDGER_*` value not exported by the hook itself. What would make it findable is not a new
capability — it is a line in the rule that auto-loads and a line in `install.py`'s hook paragraph
(M4). The prior question I could not answer from this repo is whether the hook's environment can
carry a per-dispatch value at all; if it cannot, D2's clause 1 is a decision to re-open, and the
evidence that would reopen it is the same stderr line story 02 already prints.

**2. `_grain_from_tree` reading the row's own snapshot.** Sound, and better than a walk. It reads
`stories_in_progress` — a **category** key, not one of D7's frozen five, so it is not coupled to a
deprecated family; the frozen keys are the ones removed at the next major. Reading the snapshot
rather than re-walking is what makes the grain a row names and the tree it recorded unable to
disagree, and it is free: `_tree_snapshot(cfg)` already ran three lines above. The residue is
naming, not correctness (S1).

**3. `_resolved_grain_file` swallowing a `Usage`.** The asymmetry is defensible and correctly
argued — a grain the verb guessed at must never refuse a row, and `--grain` must. It is not
*complete*, in two ways I could construct. It does not catch the exception the resolver actually
raises for a duplicate stem, so the row dies (M1) — which is the asymmetry inverted, at the worst
possible moment. And where it does catch, it says nothing, so a single live candidate whose `id`
has drifted from its path degrades the row in silence while the two-candidate case shouts (W4).
`check pm` catches the tree defect, so nothing is permanently hidden; the ledger row is.

**4. The OPEN finding in story 02's close.** In scope, and the fix is this feature's. Three
reasons. The ship criterion states the bucket clause in the feature file, so it is a criterion, not
an adjacent concern. Story 01 already crossed into `report.py` to make the positive half true and
recorded the crossing; the negative half is the same function. And the previous record's `02-4` row
already read *bucket met; "never folded" NOT VERIFIED* — this is that residue, now promised out
loud. As for which reading of the per-grain table is right: **"spend on this grain"**. The snapshot
was a proxy used because nothing better existed, and this feature is what makes something better
exist; keeping the proxy for rows that could have stated a grain and deliberately did not turns
"we could not attribute this" into "we attributed it to everyone", which is the same lie in the
other direction. The rows already written keep the snapshot — they had no choice — and that is what
`is_legacy` is for. Critically, the recorded decision cited as the reason to leave it does not say
what it was quoted as saying (W5), so nothing is being overruled by fixing it.

**5. Can the self-tests fail?** Yes, both, three ways, verified on clean `c20d5a3`:
delete the `env_arg --grain` call → `MISS — the grain travels`, 2 MISS lines, exit 1 in each hook;
pass the flag unconditionally → `MISS — an unset grain was passed as a flag`, exit 1 in each;
revert `self_test_fire` to an inherited environment with the variable exported → exit 1 in each.
The shipped files exit 0 in every one of those environments. The corpus is honest. The claim
recorded ABOUT it is not (W2), and its pytest twin is not hardened (W1).
