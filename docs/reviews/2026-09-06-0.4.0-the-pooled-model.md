# Review — 0.4.0/the pooled model (identity · pools · migration)

One record for three features, because they are one change split three ways and the seams between
them are where the defects are: `ft-identity-lives-in-frontmatter` (two stories, and its
`-decisions.md` D1/D2/D3), `ft-the-pools-are-the-tables` (`st-each-kind-has-a-configured-pool`),
`ft-the-migration-is-whole-or-nothing` (`st-the-tree-migrates-in-one-pass-or-not-at-all`).

Range `1236872 e6286a5 ae34650 73bf1ed` (identity), `be5691e 4d9fb0c` (pools), `12b9148 310fd40`
(migration), read against the two later commits that cross their seams — `d1a74eb` (the ordinal
prefix retires) and `f0a58b5` (an unbound grain is asked every question) — and re-verified at
`58730e9`, which landed under me. Read cold against `CLAUDE.md` hard rules 1-11, `SDLC.md`
§0/§5/§6, `ms-0.4.0-decisions.md`, `ms-0.4.0-handoff.md`, the three feature files, the four stories,
and `docs/reviews/2026-09-06-0.4.0-the-tree-names-what-it-lacks.md`.

Refs tool: raw `grep` over `src/ tests/ tools/ docs/`; no reference-aware search ships here. Every
behavioural claim is a live probe in a scratch `git init` repo driven with
`uv run --project <worktree> agentic-sdlc …`, never a diff read. No `make` target was run (out of
scope by the dispatch); see *What I did not verify*.

**Verdict: HOLD.** The pool layer is sound and its numbers are true — I re-derived every count
`check pm` and `check grain-shape` print on this tree and all of them hold. What does not hold is
the third feature and the compat seam. `tools/dev/pm_migrate.py` **cannot run at all** — two
symbols it calls were deleted by a later commit in this same milestone — and when the two are
restored it **silently destroys twelve files it never names**, including every milestone's
`ledger.jsonl` and this milestone's own decisions log. That is the defect the handoff records as
*"repaired, and the script fixed"*: the tree was repaired and the script was not. Separately, one
`pm new` on an unmigrated tree takes the whole tree dark, which is the promise D3 exists to make.
Do not close `ft-the-migration-is-whole-or-nothing`.

## The three recorded decisions — are they SOUND, not merely recorded

- **D1 — an undeclared `kind:` is a FINDING at exit 1, not exit 2. SOUND, and the story was wrong.**
  It turns on the right joint: a malformed *declaration* (`[pm.states.epic]`) is a config the tool
  cannot read; a grain document saying `kind: epic` is *tree content* the tool reads perfectly
  well. That is hard rule 9's own edge in rule 9's own words. The precedent is real and
  load-bearing — D4 has answered the identical question about `status:` at exit 1 since 0.1, and
  two facts of one shape answered with two exit codes would send a consumer's hook to the wrong
  file (rule 6). The rejected alternative is named with its cost, and the cost is the correct one:
  one bad document produced by a merge would abort every verb including the ones that show you
  which document. The shipped line matches the decision word for word. **The only gap is proof, not
  judgement** (`m4`).

- **D2 — an id is unique across the whole tree, not per kind. SOUND, and better reasoned than the
  story.** The story's premise was that kind prefixes make cross-kind collision impossible; D2
  kills it with a fact about the tool rather than an opinion — `pm new feature 0.1 alpha` stamps
  `id: 0.1/alpha`, unprefixed, *because the filename and the id are the author's*, which is this
  milestone's own thesis turned back on itself. A rule that is correct only while a convention the
  tool does not enforce holds is a rule that goes silently wrong the day it does not; that is
  rule 4's shape and D2 names it. The consequence is concrete and I confirmed it: `grain_index` is
  ONE dict (`model.py:1323-1352`) and `setdefault` keeps the first document read, so a cross-kind
  collision makes the second addressable by nothing. Probe confirms the shipped rule reports it.
  **Sound; the residue is the dead per-kind twin still in the file** (`m3`) **and the unamended
  story row** (`m4`).

- **D3 — the eight nested readers survive, with a stated retirement condition. SOUND AS REASONING,
  and the condition it rests on is not actually held.** The argument is right: deleting the compat
  layer would make 0.4.0 major-shaped for a benefit nobody asked for, the CHANGELOG's promise is to
  consumers and not to this repo, and *"keeping them without a retirement condition"* is correctly
  rejected as how a compat layer becomes permanent. I verified the compat layer WORKS — the
  `4d9fb0c~1` nested tree reads clean under 0.4.0 code: `check pm` PASS with `4 milestone(s),
  44 feature(s), 79 story/ies, 11 bug(s), 100 ref(s)`, `pm validate` VALID.

  that is a fact about READERS only. **No writer consults it**, so `pm new` — the first thing a

  destroys twelve files when repaired (`C1`), so the retirement condition has no working exit. The
  decision should stand; what must change is the code that makes its premise true.
