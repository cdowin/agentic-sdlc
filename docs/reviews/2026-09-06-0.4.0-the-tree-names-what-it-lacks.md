## Hard check 1 — are this repo's 62 warnings true, and is any missing?

**All 62 are true, and the count is reproducible from the tree without the gate.** I re-derived each
class from `model` directly on HEAD source: 1 no-`branch:` (`ms-0.1.0` `done`), 2 no-`handoff.md`
(`ms-0.3.0`, `ms-0.4.0`, both `building` and `in_progress`), 6 features past `todo` with no stories,
6 features + 1 milestone with no `## Ship criterion`, **15 features with no `## Proof budget`**, 28
features with no `phase:` under a `building` milestone, 3 U1 lines. Sum = 62, the gate's own number.

Spot-checks that mattered:

- **The 15 Proof-budget lines are all true and the set is exactly right.** `grep -lE '^##+ +Proof
  budget' pm/roadmap/features/*.md` returns 29; the pool holds 48 `.md` files of which 4 are
  `*-decisions.md` shared docs, so 44 features, 44 − 29 = 15. Every one of the 15 flagged paths
  genuinely lacks the heading, and none of the 29 has a present-but-empty one. All 15 are 0.2.0-era
  and past `todo` — a WARN on history, which is the right cost for a contract nothing ever verified.
- **Zero `owner:` lines is correct, not a dead condition.** Exactly one story is `building`
  (`st-a-grain-reads-its-id-and-kind-from-its-own-frontmatter`) and it carries `owner: claude`. The
  condition fires on a scratch tree (see M1's probe), so silence here is a fact about the tree.
- **U1's three lines are true**: milestone 2 of 8 in use, feature 3 of 6, story 3 of 5. No `bug` line
  because all three bug states are held (`open` 2, `fixed` 1, `closed` 8) — the rule is silent for
  the right reason, not because bugs escape `state_usage`.
- Census is honest: 4 milestones, 44 features, 79 stories (70 `done` + 8 `planning` + 1 `building`),
  11 bugs — every number matches a direct count of the pools.

## Hard check 2 — is any "absence is a finding" machinery silently disabled?

Three answers, in descending severity.

1. **Yes, for the reach of the two new WARNs** — the descent through bindings drops exactly the
   grains 0.4.0 invented. That is M1, and it is the same shape the brief warned about: a filter that
   discards the rows the line is meant to count. It is not a census defect — the unbound grains are
   counted and named by V7's census half — it is a coverage defect in the family that asks the
   questions.
2. **Yes, for the roster join, on this tree specifically** — `len(missing) == len(roster)` is
   permanently true here, so the line can never print. That is M2. It is a *deliberate* suppression
   with a stated reason, which is why it is MAJOR and not CRITICAL; but "deliberate" and "silent" are
   what rule 11 exists to separate, and the reason is knowable at the moment it fires.
3. **No dead conditions.** All three lines were fired live: Proof budget 15× on this tree, `owner:`
   and `unrun` on scratch trees built from HEAD source. None is a warning whose condition can never
   be met, and none is a census over an empty set. `_unused_states` (U1) and `_recording_findings`
   (U2) both behave correctly here: U1's `len(unused) == len(counts)` guard skips only kinds with no
   grains, U2 is silent because both ledger homes hold rows. `_unbound_rows` is gated on V7 and this
   repo's `[pm] checks` omits V7 (N4) — latent, no live consequence.
