## The claim I was told to attack: is the entry condition DERIVED?

**Yes. Five configurations, one built scratch tree each, same story id.** `_entry_condition`
(`ready_for.py:283-312`) reads exactly three runtime sources — `driver.step_names(operation)`
(which is `[<op>] steps` through `steps_for` + `validate_config`), `driver.registry_for(operation)`
for the check OBJECTS, and `steps.ENTRY_CONDITIONS` — and I could not construct a path where a
literal wins:

| `devkit.toml` | exit | census |
|---|---|---|
| *(no `[story]` section)* | 0 | `1 of 4 … (story-exists), all true; 3 at the close: story-verified (answers after the work, by \`agentic-sdlc verify --story\`), committed …, evidence-written …` |
| `steps = ["story-exists"]` | 0 | `1 of 1 … (story-exists), all true` — no "at the close" clause at all |
| `steps = ["committed", "story-exists", "story-exists"]` | 0 | `1 of 2 …; 1 at the close: committed …` (plus the duplicate-collapse line) |
| `steps = ["evidence-written", "committed"]` | **1** | `0 of 2 …` + `BLOCKED nothing was asked — … a READY over nothing asked is not a pass` |
| `steps = ["story-exists","story-verified"]`, `[story.commands] story-verified = "true"` | 0 | `… 1 at the close: story-verified (answers after the work, by \`true\`)` |

The fourth row is the one that matters most: a project whose whole declared list answers only after
the work gets exit 1 with a named blocker, not a vacuous READY — rule 4's floor, and it matches the
milestone rung's zero-feature ruling rather than the feature rung's empty-set one. The fifth shows
the project's own configured COMMAND being read back into the census sentence, which no hardcoded
list could do.

**The one literal, and why it is not a violation.** `ENTRY_CONDITIONS` is a package-level
`frozenset`. It is legitimate under rule 9 because the name space it ranges over is CLOSED to this
package: `steps_for` refuses an unregistered name in `[<op>] steps` at exit 2, so a project cannot
introduce a check whose entry-condition status the registry has not declared. The one door is
`driver.REGISTRY`, documented as a test injection seam; a check injected there is silently bucketed
as "answers after the work" (N4's second half). The blocker NAMES are derived too —
`_check_answered_by` (`ready_for.py:82-94`) reads them out of `SHIPPED_ACTION` by matching
`ready-for <rung> `, so `stories-done`/`features-done`/`findings-resolved` are the registry's words
and not the author's, and it returns `''` rather than guessing when the match is not unique.
