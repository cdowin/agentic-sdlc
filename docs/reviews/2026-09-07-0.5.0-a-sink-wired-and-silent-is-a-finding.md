# ft-a-sink-wired-and-silent-is-a-finding (U3) — review

Scope: rule U3 only. U3 and U4 shipped as one changeset and were reviewed together; the full evidence,
the five attack points and U4's findings are in `docs/reviews/2026-09-07-0.5.0-the-recording-rules.md`.
This record is split out because U4's three MAJOR findings belong to
`ft-telemetry-proves-the-path-not-the-config` and must not block a feature they are not about. That
combining them into one dispatch was the orchestrator's error, not the reviewer's.

## Ship criterion — MET, all four clauses

- A tree DECLARING `[emit]` whose sink has never been written to gets a NAMED WARN with its own rule
  id — verified for all three sink forms (`ledger` holding only a status row, a path sink, and `-`,
  which is UNVERIFIABLE).
- A tree declaring no `[emit]` gets NO line at all, with and without rows in the ledger. Opting out
  is quiet, not broken.
- The rule is reachable from `pm vocabulary`.
- The check READS. Proven by SHA-256 snapshot of every file before and after a run with U2, U3 and U4
  all firing: 0 added, 0 changed. No probe row is written to find out.

## The attack that mattered

U3 keys "did a tap write this" on the tap NAME rather than a row-kind constant, because `emit.emit()`
has no callers yet. The reviewer probed a row whose kind does not spell its tap: **the WARN fires.**
The blind direction is structurally impossible — `emit.TAPS` collides with zero ledger `KIND_*`. A kind
that does not spell its tap makes U3 noisy, never silent, which is the only acceptable failure
direction for a rule that exists to catch silence (hard rule 4).

## Not verified

`emit.emit()` has no callers, so U3's ledger sink was probed with planted rows rather than emitted
ones. When `ft-one-event-shape-serves-three-readers` mints real tap rows, U3's keying should be
re-confirmed against them — carried there rather than held open here, because the failure direction is
safe either way.

prose census (crossed at `679c726`, under an active prose pass), `test_check_hooks` (fails at every
commit in range including the 0.4.0 merge base) and `test_fresh_project`. None is this changeset's.
