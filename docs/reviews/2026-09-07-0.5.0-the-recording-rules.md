Two features, one record: they are hard rule 11 asked of two sinks, and they shipped as one
changeset in `a4545c2` (*"the entry edge, portable wiring, and the recording rules"*), read at
tree state `8f2e2c9`. Reviewed cold against both `feature.md`s, `ms-a-move-is-an-event-decisions.md`
D1, `CLAUDE.md` hard rules 3/4/5/9/10/11, and the prior record
`2026-09-06-0.4.0-the-telemetry-surfaces.md`, whose `W4` is deferred **to this milestone** and whose
subject is the predicate both new rules are built on. Refs tool: raw `grep` plus eleven live probe
trees driven through the test harness in-process — this repo ships no reference-aware search.

`src/agentic_sdlc/repo/checks/pm.py` was under an active prose pass throughout this review (980
lines at the last read, 1040 at the first; symbols unchanged, comments only). **It is not
truncated** — every rule from D1 through the R family is present and dispatched at `_run`, and the
module ends at `_verdict`. Line numbers below drift; the symbol names do not, so cite those.

**Verdict: SHIP-WITH-FIXES.** Both theses hold and both are real work. U3 is correct in every
direction I could bend it, including the one the author flagged: keying on the tap NAME fails
NOISY, not blind. U4's row-KIND question is the right question and `_hook_written` genuinely
excludes `gate`. What is wrong is that **U4 answers the right question and then gates it behind the
wrong one** — the entire rule, and the whole `telemetry-live` verdict, hang on a bare substring
search of one hard-coded settings file, which is the config read the feature is named against. Two
of the three findings below reproduce on this repo or on the topology this same changeset's shipped
guidance instructs consumers to use.

## Blockers

- **`E1` MAJOR `src/agentic_sdlc/repo/checks/pm.py` `_hook_written`** — **a hand-written `dispatch`
  row counts as evidence a courier ran, and it is doing so on this repo right now.** The predicate
  is `_kind_of(row) in set(ledger.EVENT_KINDS.values())`, i.e. `{dispatch, session}`. But
  `pm ledger record SubagentStop …` mints exactly those kinds by hand from inside the checkout —
  `_event_kind` at `src/agentic_sdlc/repo/pm/cli.py:1880-1886` — and the sibling feature deliberately
  extended that verb with `--tokens-total` for hand-recording. Measured: `pm/roadmap/ledgers/` holds
  16 `dispatch` rows, every one hand-written (no `session_id`, no `agent_id`, no usage), and
  `uv run -q agentic-sdlc check pm` prints
  `RECORDING last hook-written row: dispatch, 32m 1s ago — 16 of 3007 row(s) in pm/roadmap/ came
  from a courier`. **No courier has run.** The ship criterion's rule is *"a row written from inside
  the repo is not evidence"*; the implementation excluded one in-repo writer (the make wrapper's
  `gate` rows) and left the other (the CLI's own `ledger record`) counted as green. This is the
  feature's premise — *"`wired` alone is the tool asserting an outcome it did not observe"* — failing
  in the one line built to end it, on the tree that hosts it. Fix at the cheapest layer: the courier
  passes `--session-id`/`--agent-id` (`installables/cc-ledger-subagent.sh:330`, `ledger.ROW_KEYS`),
  hand rows do not, so require the kind **and** a `session_id`. The failure direction is safe — a
  courier row that somehow lacks one reads as `never`, which is noisy, not blind.
  **Feature: `telemetry-proves-the-path-not-the-config`.**

- **`E2` MAJOR `src/agentic_sdlc/repo/checks/pm.py` `_wired_couriers`; `conveyor/steps.py:1091-1093`**
  — **the wiring predicate is a bare substring search of one hard-coded path, and both U4 and
  `telemetry-live` gate their entire output on it** (`if not wired: return` at `checks/pm.py:602`;
  the `unwired` branch at `steps.py:1109`). Four probed consequences, all on the topology this
  changeset itself ships:
  - *Wiring above the repo — silence and a false NO.* `install.py` `SETTINGS_NAMES` now tells the
    consumer, verbatim, that the block *"works in whatever settings file your harness actually
    reads, **including one above this repo**"*. Probed a tree with no in-repo `settings.json` and a
    **1-hour-old `dispatch` row in its ledger**: `check pm` prints no U4 line at all, and
    `telemetry-live` returns `Truth.FALSE` — *"no ledger setup for this tree, no telemetry"* — on a
    tree that is demonstrably recording. The proof that recording works is in `hook_recording(cfg)`,
    already computed, and thrown away by an early return keyed on the config.
  - *`.claude/settings.local.json` is invisible.* Probed both couriers wired there (the per-user
    override Claude Code writes itself, and gitignores): U2 and U4 both silent.
  - *A false finding on an opted-out tree.* Probed a `settings.json` whose only mention is
    `{"permissions": {"allow": ["Bash(bash tools/hooks/cc-ledger-session.sh --self-test)", …]}}` —
    the allowlist entry `install-hooks`' own next-step text tells consumers to create. U4 fires the
    full WARN asserting *"cc-ledger-session.sh and cc-ledger-subagent.sh **are wired** in
    .claude/settings.json"* with no hook registered anywhere.

  Both bad directions were raised as `W4` in `2026-09-06-0.4.0-the-telemetry-surfaces.md` and
  **deferred to 0.5.0** — this milestone — with the fix already spelled: parse the JSON, look under
  `hooks`, consult both files, and say which was read. U4 was built on the unfixed predicate and
  inherits every case. The feature's out-of-scope covers *making the wiring work from any scope*; it
  does not cover **reading** it, and U4's own criterion — *"a tree whose couriers are wired … gets a
  NAMED line"* — is unmet whenever the wiring is anywhere but that one file. Cheapest fix that does
  not wait on the predicate: when `not wired` but `rec.written`, print the RECORDING line anyway —
  the ledger proves the path regardless of where the config lives — and keep silence only for
  *wires nothing AND records nothing*, which preserves the opt-out.
  **Feature: `telemetry-proves-the-path-not-the-config`** (the guidance half belongs to
  `ft-wiring-is-one-act-and-it-is-portable`; the reading half is here).

- **`E3` MAJOR `src/agentic_sdlc/repo/conveyor/steps.py:1121-1133`** — **`telemetry-live` prints
  "telemetry is live" over a ledger it could not read.** `recording_phrase` has three answers —
  `NEVER`, a kind-and-age, and `UNVERIFIABLE (…)` — and `check_telemetry_live` branches on exactly
  one of them, so the third falls through to the final `Answer.yes`. Probed: couriers wired, vehicle
  answering, `pm/roadmap/ledger.jsonl` holding an unparseable line →
  `Truth.TRUE — telemetry is live: both couriers are wired … and the last hook-written row is
  UNVERIFIABLE (pm/roadmap/ledger.jsonl could not be read)`. `check pm` U4 on the same tree says
  *"UNVERIFIABLE — not a finding, and not a pass either"*. So the belt and the gate **disagree about
  the same fact**, which is the precise failure `recording_phrase`'s own docstring says it was
  factored to prevent: *"two readers of one fact is how a belt and a gate come to disagree about
  whether a tree is recording"*. They share the reader and then read it differently. Rule 4's first
  sin, and `Answer.unverifiable` is already used twice in this same function — the fix is one
  branch. **Feature: `telemetry-proves-the-path-not-the-config`.**

## The five things I was asked to attack

1. **Can U4 be fooled into healthy by `gate` rows alone?** **No.** `_hook_written` is a membership
   test on the courier's own `EVENT_KINDS`, and the belt asserts it against a real `gate_row`. The
   whole-release blind spot is closed for that class. It can be fooled by a **hand-minted
   `dispatch`** row, which is not the criterion's named case but is the same principle and is live
   on this repo — `E1`.
2. **U3's tap-NAME keying — noisy or blind?** **Noisy, as the author claimed.** Probed a row whose
   kind does not spell its tap: the WARN fires. And the blind direction is structurally impossible —
   zero collisions between `emit.TAPS` and every `ledger.KIND_*`.
3. **Does opting out stay quiet?** **For U3, yes, in every shape I tried.** For U4, yes for the
   intended shape (no settings file), **no** for two others: an allowlist-only mention produces a
   false WARN, and `settings.local.json` produces false silence — `E2`.
4. **Do both rules READ only?** **Yes**, proven by hashing every file in the tree before and after a
   run with all three rules firing: byte-identical.
5. **Is `_wired_couriers` reading only `<root>/.claude/settings.json` a finding against U4?**
   **Yes — `E2`, MAJOR.** Not because U4 should make the wiring portable (explicitly out of scope),
   but because the same changeset's `install-hooks` now instructs consumers to put the block in a
   settings file *"including one above this repo"*, and on that topology U4 goes silent and
   `telemetry-live` returns FALSE **on a tree whose ledger holds a one-hour-old courier row**. The
   evidence is already in hand and discarded by an early return. It is also the unfixed `W4` from
   the 0.4.0 review, deferred to this milestone.

## What I did NOT verify

- **A real harness firing a real courier.** Every `dispatch`/`session` row in every probe was minted
  through `ledger.usage_row`/`pm ledger record`. `E1` is precisely the claim that those are
  indistinguishable from the real thing, so this gap is the finding, not a hole in it. I did not
  root a session above this checkout and dispatch an agent to confirm the end-to-end path.
- **`emit.emit()` in anger.** It has no callers, so U3's ledger-sink case was probed by planting rows
  by hand rather than by emitting. Whether a real tap's row lands in a file `_ledger_paths` covers is
  therefore argued from `emit._sink_file` sharing `ledger.grainless_path`/`ledger_of_grain`, not
  measured. One gap I did trace: a grain owned by an **archived** milestone is excluded from
  `model.milestones(cfg)` and so from `_ledger_paths`, while `emit` would still write there — U3
  would over-report. Noisy direction, not filed.
- **Whether `session_id` is always present on a courier row.** `E1`'s proposed fix rests on it;
  `cc-ledger-subagent.sh:330` passes `--session-id` from the hook payload conditionally
  (`env_arg`), and I did not confirm the harness always supplies it. The failure direction is safe
  either way.
- **Consumer-side effects of the new output shapes.** Hard rule 6 makes `RECORDING …` and the U3/U4
  WARN strings a grepped contract. They are new lines, so nothing breaks, but no consumer tree was
  run against them.
- **The two inherited red tests.** I bisected `prepare-commit-msg` to establish that this changeset
  did not cause `test_check_hooks`, and read the `check doc` failure message only. Neither root
  cause was diagnosed — both are outside this scope.
- **`checks/pm.py` under concurrent edit.** The prose pass moved the file three times during this
  review. Every probe ran against the working tree at the time it ran; the symbols and behaviour
  were identical across all of them, but I did not re-run the full probe set against a frozen
  archive.
