**Verdict: SHIP-WITH-FIXES.**

The two claims I was told to attack hardest both hold.

**The skip cannot pass a check silently, and it cannot pass one the project did not declare.**
I could not construct an accepted `--skip` that fails to print its own line, and the reason is
structural rather than incidental: `skippable_for` refuses any `skippable` entry that is not in
`[<op>] steps` (`steps.py:431-436`), so `declared ⊆ names`, so an accepted skip is always a name the
`run` loop walks and always prints `[op] skipped: <check> — "<why>"` with the reason (`driver.py:258-263`).
All four config refusals and all four flag refusals were probed live and are exit 2, by name, with
nothing written and the skipped check never called. Stock is byte-identical: diffing the shipped
output lines against `a05a378`'s driver, the only two changes are the new `skipped:` line — which
fires only when a skip was given — and the `adopt` census, which renders `f'{len(names)} check(s)
true'` verbatim when `dispositioned` is empty. `--force` is untouched and does not bleed.

**The clock sums, and it does it off arrival rows with no hook in sight.** I recomputed
`ms-0.4.0` independently from the two ledger files: `ft-binding-is-a-field` 861 = 421 + 440, and the
milestone's 4069 is the sum of the eight stories that hold time (562+580+544+440+421+489+507+526).
Same on `ms-a-move-is-an-event`: 3820 + 6×1879 = 15094. Mutating `arrival_state` to be blind to
`disposition` rows turns the disposition-only leg from `{'building': 600}` into `{}`, so
`test_one_move_is_one_arrival_however_many_rows_carry_it` genuinely fails on it — the hook-free
claim is proven, not documented.

What holds fixes is narrower and specific. `pm ledger report` **refuses a feature or story id**
(T1), which is half of that criterion's first sentence. And the clock's discard census was **not
extended to the row kind this feature added** (T2): a `disposition` row naming a grain the milestone
does not hold is dropped with no line saying so — the exact hole `_in_flight_ages`'s own docstring
says it exists to close, reopened, and it bites in precisely the "disposition rows alone"
configuration the criterion asserts.

## D12 — is the revision honest? (attack 4)

**Yes, and it is the smallest revision that buys the economy.** D12 (`ms-0.2.0-decisions.md:445`)
says *"Every check runs and every failing one prints, then: all true → the one write; any false → a
clean error naming each failing check and NO write, exit 1."* D5 breaks exactly one clause of that
— **a skipped check is not run** — and says so in the decision, in the module docstring and in
`--help`, rather than letting it be discovered. Every other clause survives verbatim, and I checked
each against the code:

- **at most one write.** `run` still calls `write` once (`driver.py:314`). The `disposition` row is
  not a second belt write: D6 folded it into the arrival `pm` was already minting, and the belt
  hands the judgement *into* that write as an argument (`_writer`, `driver.py:589-608`). One act,
  one row. `test_a_declared_skip_is_never_asked_and_rides_the_arrivals_one_row` pins the row list at
  exactly `[status, disposition]`.
- **every check is named on its own line.** Verified structurally above.
- **a false check with nobody speaking still writes nothing.** `if false and not force` is unchanged
  (`driver.py:308`).
- **the two records do not bleed.** Probed and tested: `deviation.step` names only the false check,
  the `skipped` field names only the answered one, and neither string appears in the other row.
- **a refused close leaves no judgement behind.** This is the ordering D6 bought and it is real:
  the belt collects and emits at the arrival, so `test_a_refused_close_leaves_no_skip_behind_it`
  asserts an empty ledger after a refusal.

The belt is still "its checks, then one write". What changed is the answer set, and D5's three-value
table (`true` / `dispositioned` / `false`) is a faithful description of what the code does.

## Findings

### `ft-time-is-measured-per-state-and-rolls-up`

- `T1` **MAJOR** `src/agentic_sdlc/repo/pm/cli.py:2486-2489` — **the criterion says the id names any
  level; the verb takes a milestone id only.** The criterion's first sentence is *"`pm ledger report
  [<grain-id>]` reports seconds per STATE, per grain, at whatever level the id names — milestone,
  feature or story"*. `_report_milestone_dir` refuses anything else at exit 2: *"'ft-x' is a feature,
  not a milestone — the ledger is per milestone (D6), so name one"*. The `--help` synopsis
  (`cli.py:318`) still reads `ledger report [<milestone-id>]`. The *measurement* half of the
  criterion ships in full — the clock block carries one row per grain at all three levels, rolled —
  so what is missing is the addressing, which is the half an operator types first. **Fix, one of
  two, and it is a decision not a patch:** accept a feature/story id and narrow the report to that
  subtree (the walk already produces the rows; only the mdir resolution and the heading change), or
  amend the criterion to `[<milestone-id>]` and say the level comes from the row, not the argument.
  The refusal is clear and points at the milestone, so nothing here lies — it is a criterion clause
  that is not met, raised at MAJOR so it gets dispositioned on purpose rather than read as shipped.

- `T2` **MAJOR** `src/agentic_sdlc/repo/pm/report.py:959` and `:1352-1360` — **the clock reads two
  row kinds and its discard census counts one.** `clock_data` keeps a row only when
  `gid in kinds` (`:959`), so any row naming a grain this milestone does not hold is silently
  dropped — `disposition` rows included, since this feature made them arrivals. The only disclosure
  is `_in_flight_ages`'s `unplaceable`, which iterates `status` rows alone (`:1352-1358`) and prints
  *"N status row(s) name a grain this milestone does not hold, so no age was measured from them"*.
  Probed on a scratch tree with a re-parented story whose only rows are two `disposition` rows
  1800s apart: the milestone reports `closed_s -` and the report prints **no** line about rows it
  discarded. With `status` rows present the sibling row triggers the line, so today's `pm`-written
  ledgers are covered by luck — but this feature's headline claim is that the report is complete
  from disposition rows ALONE, and that is exactly the configuration where the disclosure vanishes.
  `_in_flight_ages`'s own docstring names this as rule 4 (*"a status row … was DISCARDED, so a tree
  whose ledger names renamed ids reported `[]` — and nothing saying one had been attempted"*); the
  new row kind reopens it. **Fix:** count discards over `arrived` rather than `status` — the list is
  already computed at `report.py:1068` and passed to `clock_data` — and say "arrival row(s)", not
  "status row(s)".

- `T3` **MINOR** `src/agentic_sdlc/repo/pm/report.py:923-926`, `src/agentic_sdlc/repo/pm/cli.py:318-342`

  findable — that is why this is MINOR and not MAJOR. **Fix:** put `CLOCK_COLUMNS` and
  `ACTOR_COLUMNS` into the `ledger report` help text, or delete the constant and its claim.

- `T4` **MINOR** `src/agentic_sdlc/repo/pm/report.py:1124`, `:1352`, `src/agentic_sdlc/repo/pm/ledger.py:624/638`
