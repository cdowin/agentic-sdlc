**Verdict: HOLD.** The mechanism is right and its proof bites — I mutated the digest to drop
`--others`, silenced the reuse print, and made `_verdict` accept an unparseable `ts`, and each time
the named case went red and no other did. The trust boundary in `_verdict` is the most careful code
in the milestone. What holds the line is three things it does not see or does not deliver. The
digest excludes the ledgers, and `check budget` — inside `make milestone`, which IS the milestone
rung — grades on exactly the file it excludes: I flipped that gate PASS → FAIL with one appended row
while the digest stayed byte-identical (E1). A submodule's checked-out commit contributes a
constant, so a superproject whose own `git status` says `M lib` reuses a stale green (E2). And the
economy the feature exists for does not arrive: **two `close feature` runs on an unchanged tree ran
`make test` twice**, because the belt's one write — the grain's `status:` line, D12's whole point —
is a tracked byte inside the digest (E3). The CHANGELOG asserts the saving as shipped fact.

## Findings

- `E1` **MAJOR** `src/agentic_sdlc/repo/verify/cache.py:154-170` (`_excluded`) —
  **the ledger exclusion hides a change that flips the milestone rung's own verdict.**
  `[verify] milestone = "make milestone"`; `make milestone` is `check` + `matrix` + `budget`; and
  `checks/budget.py:75` reads `ledger.grainless_path(cfg.roadmap)` — the exact file `_excluded`
  drops — grading `the NEWEST gate row per name` against `[tests] budget`. Probe, scratch repo,
  `budget = { unit = 30 }`, one `gate` row at 10 000 ms, then ONE row appended at 99 000 ms:

      A1 check budget -> 0 ['[check:budget] PASS — within their time budget: unit']
      A2 check budget -> 1 ['[check:budget] FAIL — 1 tier(s) over budget: unit. …']
      A  digest before: 83419687cd8d 3
      A  digest after : 83419687cd8d 3
      A  SAME DIGEST  : True

  So `verify --milestone` can report `REUSED PASS` over a tree whose `make milestone` would now
  exit 1. That is rule 4's first cardinal sin with a record behind it, and the row that causes it
  is the one **the previous run filed about itself** — the author's own "the run's own leavings"
  argument is what makes the hole, not an oversight. `check pm` reads the same ledgers
  (`checks/pm.py:397-417`) and is in the same `make check`.
  **Not resolvable by deleting the exclusion** — every gate writes a cost row, so a digest that
  covered them would never repeat and the feature would be dead. The two honest answers are to
  exclude by ROW KIND rather than by file (the digest hashes only rows the gates do not write —
  costly), or to state the exception where the operator stands: a third `[verify:cache]` line on
  the milestone rung naming what the reused verdict did NOT re-measure. Blast radius is bounded
  today: `release`'s `gate` check is `make milestone` directly (`conveyor/steps.py:80`), not
  `verify --milestone`, so this reaches an operator typing the rung by hand, which
  `CLAUDE.md`'s ladder and `pm-execution.md` both tell them to do.

- `E2` **MAJOR** `src/agentic_sdlc/repo/verify/cache.py:140-142` (`_content_of`) —
  **a submodule's checked-out commit contributes the constant `MARK_DIR`, so rolling it is
  invisible.** The comment names the case exactly — "A submodule: one path in `ls-files`, another
  checkout's state" — and then returns a constant for it. Probe, real superproject with a real
  submodule, rolled back one commit with `git -C lib checkout <first>`:

      B  ls-files: ['.gitmodules', 'a.txt', 'lib']
      B  submodule f.txt now: one
      B  digest before: 534a6a80385e 3
      B  digest after : 534a6a80385e 3
      B  SAME DIGEST  : True
      B  superproject git status: 'M lib'

  Git itself calls this a modification of the superproject and the digest does not move, so a
  consumer with vendored code in a submodule gets a reused green over a tree that changed. Rule 8
  forbids excusing this because this repo has no submodules. The fix is small and belongs in
  `_content_of`: for a listed path that is a directory, contribute
  `git -C <path> rev-parse HEAD` plus whether `git -C <path> status --porcelain` is empty — or,
  if that is too much git for this module, refuse the state (return `None` with a defect) the way
  a 0-file tree is refused, which fails toward re-running.

- `E3` **MAJOR** ship criterion, last line — **"Closing N features on an unchanged tree costs one
  gate run and N-1 reads" does not hold, and the CHANGELOG states it as shipped fact.** A belt is
  its checks, then ONE write (D12), and that write is the grain's `status:` line — a tracked byte
  inside the digest. So close #1's write is precisely what invalidates close #2's state. Probe, a
  scratch milestone with two `reviewing` features each holding one `done` story, `feature = "make
  test"` counting its runs to a file outside the tree, **no prior `verify`**:

      close feature alpha: exit 0   [feature] ok: feature-verified — … $ make test
      close feature beta : exit 0   [feature] ok: feature-verified — … $ make test
      TARGET RUNS: ['test', 'test']

  Attribution, on a second driver: restore **only** the `status:` line in `alpha/feature.md` after
  the close and the digest returns to exactly its pre-close value —

      state before closes: c9d7ca811921 10 -> after alpha close: d37c037f40b3 10
      ATTRIBUTION: restore ONLY alpha feature.md status -> c9d7ca811921 | equals pre-close: True

  The file count stays 10, so the ledgers ARE correctly excluded; the one-line status write is the
  sole invalidator. Seven closes are still seven 90 s suites. What DOES work is the read the
  criterion's first sentence describes: a second bare `verify --feature` on an unchanged tree
  reuses and says so, and a `close feature` run straight after a green standalone `verify
  --feature` reuses too (probe B). So the mechanism is sound and the delivery is not.
  CHANGELOG.md:99 asserts the saving; either the belt has to hand the rung a state computed before
  its own write is planned, or the claim comes out of the CHANGELOG and the criterion. The former
  is a real design question — a feature document IS input to `check pm` inside `make milestone`,
  so excluding grain documents from the digest is a new E1 — and it is bigger than a fix-in-place.

- `E4` **MINOR** `tests/test_conveyor_close.py:152-166` — **the snapshot exclusion is legitimate in
  principle and broader than it needs to be.** Ruling on the author's argument, which the caller
  asked for explicitly: it is CORRECT that D12's "one write" is a grain's status and that a check a
  belt RUNS may file telemetry about its own run — the gate wrapper already appends a cost row on
  every real gate (`tools/dev/gdk_gate.sh`, `_gdk_ledger_record`), so the grainless ledger already
  moved during a belt refusal on any tree with the devkit gates wired. The exclusion does not
  invent an exception; it names one that existed. **But it is spelled as a whole-file exclusion
  where a kind filter would do.** Four assertions lose reach — `:198` and `:275` ("the belt wrote
  over a false check" / "over a red rung"), `:245`'s `changed == {SFILE, LEDGER}`, and `:379` —
  and what they can no longer see is a row naming NO grain written during a refusal. That is a real
  shape: `ledger.ledger_for` files a `deviation` row grainlessly when the grain resolves to no
  milestone. Keep the file in the snapshot and assert its rows are only `gate`/`verify` kinds;
  the assertion survives and the telemetry is still allowed.

- `E5` **MINOR** `tests/test_verify_main.py:519-568` — **eight scratch repos and eight `make`
  spawns to prove a pure function refuses a row.** `.claude/agents/reviewer.md` checklist item 5
  and hard rule 10 both name this: "a test that spawns to check a pure function", "a function call
  before a temp tree, a temp tree before a process". Seven of the eight cases are
  `cache._verdict(row) is None`; only the control ("a row this CAN read") needs the end-to-end run
  to prove the wiring. It has a cost beyond time: the module spawns, so `tests/conftest.py` derives
  the `shell` mark and `pytest -m "not shell"` deselects all 25 cases — **the story rung, `make
  unit`, never exercises the trust boundary at all**, and that boundary is the single piece of this
  feature that can commit rule 4's sin. Split the seven into a `_verdict` table in the unit tier and
  leave the control where it is.

- `E6` **MINOR** `src/agentic_sdlc/repo/verify/main.py:200-215` — **the state is read before the run
  and never re-read after, so a tree edited DURING the target records a verdict keyed to a tree the
  target did not fully read.** The comment defends the placement ("the state a verdict is about is
  the tree the target read"), and the placement is right; what is missing is the second half. A
  90 s `make test` with an agent editing under it, then a revert, hands a later run a green that was
  never true of that state. Cheap fix, same shape as everything else here: recompute after the run
  and record only when the two agree, else print that the tree moved mid-run and record nothing.

- `E7` **MINOR** `src/agentic_sdlc/repo/verify/cache.py:83-111` — **nothing outside the working tree
  is in the state, and there is no age bound.** `make matrix` — inside the milestone rung — runs
  every interpreter in `PY_MATRIX`, and installing or removing a python moves no byte git lists;
  `.venv*/` is `.gitignore`d by design. So a verdict is reused across a toolchain change on a
  byte-identical tree, at any age. The age IS printed, which is the mitigation and the reason this
  is MINOR rather than MAJOR — but nothing refuses a stale answer, and the operator who reads
  `(3 weeks ago)` and moves on is the failure mode. Consider a configurable maximum age, or at
  minimum name the interpreter in the row so a mismatch can be said out loud.

- `N1` **NIT** `src/agentic_sdlc/repo/verify/cache.py:182-189` — `verify --story` in a tree with a
  `[verify]` section, no `[pm]` section and no PM tree at all **creates `pm/roadmap/ledger.jsonl`
  and its two directories**, silently. Probed: a bare repo with three files came back with
  `?? pm/` in `git status`. The write is by design and the precedent (the gate wrapper) exists,
  but the first run says nothing about having written anything. Record only where the roadmap
  directory already exists, and say so when it does not — the defect string `record()` already
  carries is the right sentence.

- `N2` **NIT** `pm/roadmap/features/ft-verify-remembers-its-last-green.md` proof budget — names
  `lands in: tests/test_verify.py`, a file that does not exist (the module is
  `tests/test_verify_main.py`), and `tier: pyunit` where the cases correctly land in the `shell`
  tier. `cases: 5` is exact. Fix the budget, not the tests.

- `N3` **NIT** `src/agentic_sdlc/repo/checks/pm.py:507-527` — `_tree_has_a_row` counts **raw
  non-empty ledger text** on purpose, so a `verify` row now makes U2 permanently silent on any tree
  where anyone ran a rung once. This is the exact failure U4's own docstring records ("the ledgers
  were not empty — they held the rows this checkout writes itself"), and U4 still fires correctly
  because `KIND_VERIFY` is not in `ledger.EVENT_KINDS`. So the sibling feature already covers it;
  worth knowing that this changeset made U2 one notch quieter.

- `N4` **NIT** `src/agentic_sdlc/repo/verify/cache.py:161,168` — `_excluded` drops the **whole**
  `ledger.ledgers_dir(cfg)`, whose location is the consumer-settable `[pm] ledger_dir`. Pointed at
  a source directory it would silently exclude real inputs from the digest; pointed at the repo
  root it fails safe (0 files → no state → no reuse). Exclude by file name and extension inside
  that directory rather than by directory.

- `N5` **NIT** rule 11's second half — **`--no-cache` is unreachable through the belts and unnamed
  in every shipped guidance surface.** `close story` and `close feature` spawn
  `agentic-sdlc verify --<rung>` with no way to force, and `grep -rn no-cache` over
  `src/agentic_sdlc/repo/installables/`, `src/agentic_sdlc/repo/pm/guidance/`, `.claude/rules/`,
  `SDLC.md` and `docs/sdlc-protocol.md` returns nothing. The operator standing in the rule that
  auto-loads reads "`verify --story` — what `[verify] story` names" and learns nothing about a
  reusable green. `--help`, README and CHANGELOG all carry it, so this is a DELTA for the
  tech-writer, not a blocker.

- `N6` **NIT** `src/agentic_sdlc/repo/verify/cache.py` — 76 prose lines against 209 code lines
  (**0.36**) in a tree whose aggregate ceiling is 1/3 and which spent this whole milestone within
  0.0002 of the line. The prose is good prose and it is load-bearing on a change this dangerous;
  it is also the densest new module in the changeset. Nothing to fix now — the census was green in
  the working copy when I finished — but it is the file to trim first if the census reddens again.

## What I did NOT verify

- **`make test` and `make milestone` never ran.** So "the change passes the feature and milestone
  rungs" is unverified by me; `make precommit` I did run, and it was red for the reason in N6.
- **No cross-machine or CI reuse was exercised.** I reasoned that a committed `verify` row can never
  match — committing the ledger moves HEAD, and HEAD is in the digest — but I did not push a row
  through a second checkout to prove it, and "caching across machines" is out of scope by design.
- **No concurrency probe.** E6's mid-run edit is reasoned from the code, not raced.
- **No large-tree cost measurement beyond this repo.** `tree_state` here is 102-157 ms over 439
  files; it hashes every byte of every listed file, so a consumer with large binary assets pays
  proportionally, on every rung including `--no-cache`. Unmeasured.

  file that is already ~329 KB and TRACKED here, re-read and JSON-parsed in full by `recorded()`

- **I did not read the sibling 0.5.0 features**, and `ledger.py`'s `retire_row` /
  `ledger_of_grain` in the same diff are out of this scope.
