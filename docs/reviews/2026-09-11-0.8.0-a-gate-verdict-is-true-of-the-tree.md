## Findings

**M1 (MAJOR, open) — `src/agentic_sdlc/repo/checks/pm.py:497-503`, `src/agentic_sdlc/repo/pm/skills.py:258`,
`src/agentic_sdlc/repo/pm/inventory.py:1449`: after `pm rename`, U1 says `fixed never held` again and
gives a false reason.** Probe: a scratch tree with four bugs moved `open → fixed → closed` by
`pm bug`, then `pm rename bg-crash-<n> bg-kept-<n>` on each. `pm rename` is the tool's own verb, and
it rewrites frontmatter but not the ledger. `check pm` then prints ``bug: 1 of 3 held, open, fixed
never held … 16 ledger row(s) naming a grain no longer in the tree skipped``, although all four
grains are still in the tree. That fails ship-criterion bullet 4. The headline "named by no ledger
row" is false whenever any row is skipped. On this repo the line reads `280 ledger row(s) naming a
grain no longer in the tree skipped`, but 276 of those rows name 121 grains that are still in the
tree under ids renamed from the pre-0.4.0 path form (`0.3.0/documented-behaviour-is-the-behaviour`
became `ft-documented-behaviour-is-the-behaviour`; counted by slug match, three checked by file).
No state on this repo is misreported, because every state a renamed grain held is also held by a
live grain. Here, only the clause is false. The skip itself is forced: a renamed id has no kind to
read, and guessing one crosses rule 9. So the fix is the words. Write ``N ledger row(s) naming an id
no grain in the tree declares (retired, or renamed: `pm rename` does not rewrite the ledger)
skipped``, and when N > 0 qualify the headline to "named by no ledger row it could place". Make the
same change in `pm init`. Following renames (a row that `pm rename` appends) is a new capability and
belongs to a later grain. This is MAJOR rather than MINOR because the feature exists to make these
verdicts true, and it ships a new false sentence into `make check` on its own tree.

**M2 (MAJOR, open) — `src/agentic_sdlc/repo/installables/ci-semver-gate.yml:115-128` and `:180`
(and the installed `.github/workflows/semver-gate.yml`): the incremented-hotfix rule admits a bump
when main is a RELEASE, not a hotfix.** The rule only asks whether main minus its last component is
the version or id of a done milestone. Probe: the compare step extracted with the test's own
`_compare_step_script()`, run pre-fix and post-fix over scratch roadmaps. Done `0.16` and `0.16.1`
(the layout `COMPARE_ROWS` row 3 supports), main `0.16.1`, PR `0.16.2`, with no milestone declaring
`0.16.2`. Pre-fix this is refused with `::error::`. Post-fix it prints ``Version bump OK: 0.16.1 ->
0.16.2 (incremented hotfix 2 over main's 0.16.1, on 0.16, the id of done milestone 0.16)``. A second
case has the same shape: done `0.28` and `0.28.4`, main `0.28.4`, PR `0.28.5` that no milestone
declares, and the gate says OK. That is AC2's own refused example ("skipping to `0.28.5` with no
done `0.28.5`"), and it gets through because main is a release. AC1 requires main to be "already a
hotfix", but `0.16.1` is a done milestone's own version, so the OK line's label is false too. A
`building` milestone at the PR's version is still refused (probed), so what gets through is a bump
that no milestone declares at all, which is the case the gate exists to stop. Only trees with
mixed-length done versions are exposed, and this repo has none. Fix: in the loop, set `main_done`
when a done milestone's `version:` or id equals `$MAIN`, and use `incremented` only when
`main_done` is empty. Add both probes to `COMPARE_ROWS` as refusals. The fix refuses nothing
legitimate: a hotfix of release `0.16.1` is `0.16.1.1`, and the appended rule already admits it.
This is MAJOR because it is sin (a) in a gate that every consumer PR runs, and the fix is cheap.

## Rule 6: line shapes that changed

1. The `check pm` retired-field DRIFT line changes from ``… — <why> (D11)  [path]`` to
   ``… — <why>; delete the line by hand, no `pm` verb removes a field  [path]``. It now prints
   before D4 and the walk, not after CONTAINMENT. A grep for `(D11)` no longer counts these;
   ``carries `fix_milestone:` `` still matches.
2. A new line: `  ROSTER  [pm] checks omits N of 12 stock-on rule(s): …`. It is additive, but a
   parser keyed on the known prefixes will meet a new one.
3. The U1 WARN changes in three places:
   - `have never been held by any grain in this tree` becomes `are held by no grain and named by no ledger row`.
   - `N of M in use` becomes `N of M held`.
   - The "a flow the project is not running" tail becomes `read from …`, with optional skipped and
     unreadable clauses.

   Greps for `never been held` or `in use,` break; `never held` and `(U1)` still match.
4. In the `pm init` ladder, the "flow you are not running" sentence becomes a sentence saying what
   was read, with optional skipped and unreadable lines. `this tree uses N (…)` now counts states
   the ledger shows were held.
5. The retired-rule ERROR still exits 2. For D3 and D8, `Remove it from the list.` becomes
   `Removing it alone turns the question off: replace D3 with D11 in the list.`, and D3's text
   loses "Containment is unconditional". D7 and the V retirements keep the old ending.
6. `check pm --help`: the opening line and the default roster.
7. `check doc`: line shapes are unchanged. A finding for a wrapped span names the line the span
   starts on. New findings can appear, which is the minor bump the story declares. The `--help`
   docstring changed.
8. The semver gate's OK line changes from `(hotfix N on main's X)` to
   `(appended hotfix N on main's X)`, and there is a new `(incremented hotfix …)`. The `::error::`
