## The findings

**R1 — MAJOR — `install-hooks --force` on a pre-0.5.0 consumer leaves a hook that aborts every agent commit.**
The walk printed *"wrote tools/hooks/prepare-commit-msg — kept its project-config header line for
line …; the kept header LACKS `TRAILER_RE=`, which the packaged one declares — copy it in from
--diff"*. The packaged body reads `$TRAILER_RE` under `set -eu`
(`installables/prepare-commit-msg:12,136`). Results:

- `git commit` with no agent scope: exit 0, because the hook exits at `is_agent_context`.
- `DEVKIT_AGENT_SCOPE=1 git commit -m … -- README.md`: *"tools/hooks/prepare-commit-msg: line 132:
  TRAILER_RE: unbound variable"*, commit exit 1.

`adopt`'s `installables-current` says `ok`, naming the lack as a note. Two gates do tell the truth
here: `check hooks` FAILs on the hook's own self-test, and so does `adopt`'s `hooks-self-test`. So
this is not sin 1. But rule 3 says a verb that cannot guarantee a correct result refuses, and
`--force` computed the lack and wrote anyway. D3.3
(`ft-install-force-keeps-what-the-project-owns-decisions.md:77`) calls a missing key the project's
choice, and for a key a `set -u` body reads it cannot be. The install review's M6 probed a missing
`GATE_STATIC`, not this natural bump case. Every consumer installed at or before 0.4.0 hits it,
which includes both filers. **MAJOR because it is the walk's own outcome on the milestone that is
named for it.** Fix shape: NEEDS YOU 1.

**R2 — MAJOR — Ship bullet 5 is not met: the installed rule says a story fills its slots without a name.**
`pm-execution.md:131-134` says: *"`<name...>` is required to create a milestone, feature or story;
… Give an id already in the tree and omit the name to fill missing slots instead."* Results:

- `pm new feature ms-first-light login` on an existing feature: *"already has every canonical slot
  (no-op)"*.
- `pm new story ft-login form` on an existing story: exit 2 and the usage block, because
  `cli.py:2184` `if len(rest) < 3: raise Usage(USAGE)` runs before any existence check.

v0.7.0 behaves the same. This range made the kind list explicit, which is what makes the sentence
false for story. `pm-operations.md:78` already says it correctly (*"`new milestone` and `new
feature` are idempotent"*). The cheapest layer is the word. Making the story path match the feature
path is the alternative.

**R3 — MAJOR — the no-name hint for `pm new feature` is a printed command that does not run.**
`make pm ARGS='new feature ms-first-light nameless'` prints *"<name...> is required: `make pm
ARGS='new feature '"'"'ms-first-light nameless'"'"' <name...>'`"*. Pasting it with `Nameless` for
the slot gives *"no milestone resolves from 'ms-first-light nameless'"*, exit 2. The cause is
`cli.py:2175` passing `f'{mid} {slug}'` as one element to `vehicle.command`, which has quoted any
spaced value since `1549c46`. The milestone form (`new milestone m2`) renders correctly.
`test_a_create_with_no_name_names_the_argument_not_a_missing_grain` asserts the words and never
the argv. **MAJOR because the milestone's northstar is "every command the kit prints runs", and
this is a one-line fix.**
