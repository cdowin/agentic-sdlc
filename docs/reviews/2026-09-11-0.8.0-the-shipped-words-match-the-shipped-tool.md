## Findings

**M1 (MAJOR) — the stock pm-operations skill binds bugs the opposite way to the new stock
`bugs bind:`, and the brief says the skill wins.** `src/agentic_sdlc/repo/pm/guidance/pm-operations.md:61`
is installed as `.claude/skills/pm-operations/SKILL.md`, a file the consumer cannot edit, and its
schema line is `bugs/<slug>.md  milestone: the one that will FIX it`. `installables/pm-operator.md:27`
now ships `bugs bind:  the milestone-of-catch`, and the same fence's `pm skills:` line (`:29-31`)
says *"load them first; if a skill disagrees with this file, the skill wins"*. Both files are in cA
after `pm init` and `install-agents`. So a stock pm-operator gets two contradicting instructions and
a tie-break that discards the line this story created. That is #23's own complaint (*"the agent then
reads two contradicting instructions"*), now between two stock files and with no override involved.
AC 3's grep passes only because the words differ: `git grep -n -E 'milestone-of-catch|will FIX it'
-- src` → `pm-operator.md:27`, `pm-operations.md:61`. Fix, using the story's own split (the stock
body states the fact, the fence states the policy): change `pm-operations.md:61` to
`bugs/<slug>.md                 milestone: <milestone-id>   ← its parent (which one: bugs bind:)`,
run `pm install-skills --force`, and widen AC 3's grep to both phrasings. The alternative is to change
the stock default to "the milestone that will fix it", which the story's Out of scope names as the
default the model implies. That is a decision for Chris.

**M2 (MINOR) — `installables/pm-operator.md:64-65` and `installables/tech-writer.md:60-61`:
*"that milestone cannot close while the bug is open"*.** In cA, `pm milestone done ms-alpha` with
bg-bone `open` → `milestone ms-alpha: planning -> done`, exit 0 (by design, `pm-execution.md:151`).
After `pm bug fixed bg-bone`, `pm ready-for milestone ms-alpha` → `BLOCKED  bg-bone is fixed — a bug
nested in ms-alpha`, exit 1. The sentence holds for `release 0.1.0` (`features-done: BLOCKED bg-bone
is open`, exit 1) and for `check pm` (D11 DRIFT, exit 1), but not for the move itself. Also, `open` is
the bug's todo word, and `fixed` blocks as well. Fix, in both files: "a bug's `milestone:` is its
parent: `release` refuses that milestone until the bug is in a `done`-category state (`closed` in the
seed), and `check pm` D11 fails a milestone moved to `done` first."

**M3 (MINOR) — `tests/test_install_sdlc.py:165`, the case named "every registry sentence names what
its check reads", holds 5 of the 23 sentences to their input.** The retired-word loop covers all 23
`STEP_DOC` entries. The input table (`:181-187`) covers the five release checks it lists. Probe:
`pytest -m "not shell" tests/test_install_sdlc.py -k test_every_registry_sentence`. Baseline: `1
passed`. With the #33 sentence restored: `1 failed`, `AssertionError: ('changelog-unreleased-nonempty',
'Unreleased', …)` at `:177`, so the case catches the drift that actually happened. Then `version-sync`

(its check reads and never bumps), and `stories-done` to "the feature file lists its stories and each
is ticked.": `1 passed`. Protocol AC 3's "or no longer matches what its check reads" is met for 5
sentences. Fix: rename the case to what it measures,
`test_no_registry_sentence_names_a_retired_input_and_each_release_check_names_its_input`, or give the
other 18 a token each.

**M4 (MINOR) — `src/agentic_sdlc/repo/conveyor/steps.py:1601-1603`, rendered at
`docs/sdlc-protocol.md:38`, describes `features-done` as passing on less than it checks.** The text is
*"every feature is in the `done` category and no open bug names the milestone"*. The rendered protocol
is one of the four surfaces the ship criterion covers. In cA, `pm feature done ft-ftwo` →
`planning -> done (no review record)`, then `pm ready-for milestone ms-alpha` → `BLOCKED  ft-ftwo is
done, reviewed: is blank — no review record is named`, exit 1. A `fixed` bug blocks too (M2). The
installed rule gets it right (`pm-execution.md:51`, "every feature done with a review record"). Fix:
"`pm ready-for milestone <milestone>` exits 0 — every feature is in the `done` category and names a
review record in `reviewed:`, and every bug bound to the milestone is in the `done` category." Then
run `install-sdlc --force`.

**M5 (MINOR) — `src/agentic_sdlc/repo/pm/guidance/pm-execution.md:130-131`: *"`<name...>` is
required to create"*.** This stopped being true for a bug at `65b7a5e` (pm-surface, #24). In cA,
`pm new bug ms-alpha nameless` → `next: pm set bg-nameless name '<name>' — name: is empty…` /
`created pm/roadmap/bugs/bg-nameless.md`, exit 0. `pm new milestone beta` and `pm new feature
ms-alpha fnoname` → `<name...> is required`, exit 2. The installed rule is false at v0.8.0 in the
harmless direction: an agent that follows it always gives a name. Fix: "`<name...>` is required to
create a milestone, feature or story; a bug is created without one, and a `next:` line names its empty
`name:`. Give an id already in the tree and omit the name to fill missing slots instead." Then run
`pm install-skills --force`. Whichever of this feature or `ft-the-pm-surface-has-no-dead-ends` lands
last owns the fix. This feature's criterion is where the claim is measured.

**M6 (MINOR) — `README.md:50-51` gives `agentic-sdlc changelog <milestone-id>`, and a reader has a
