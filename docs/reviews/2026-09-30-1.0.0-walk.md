## Writers vs the snapshot

The snapshot (`inventory._held`) is keyed on `core.apply.mutations()`, and `_run` counts every step. Raw mutators in `src/` outside `core/apply.py`: grep finds only `ledger.append_to` (`open('a')`). So `frontmatter.write_raw`/`set_field`, `templates.scaffold`, renames, retire deletions and `_as_written` (set, then restore through `write_raw`/`set_field`) all drop it. `_pm_run` and the belt's `_writer` call `pm_cli.main` in process, so they nest and share the scope, and their writes are counted. No git subprocess writes the tree.

## Findings

- **W1 WARNING** `repo/pm/arrive.py::run_gates` (spawn at :535): a `[pm] arrival_gates` `make` child that writes grains is invisible to later reads in an enclosing scope. The builder says it is the verb's last step. That is true for a bare `pm` call. It is false under the belt driver's outer `reading_tree()`: `close story a b` makes one in-process write per grain, and the scope outlives each nested verb. This repo declares no arrival_gates, so it cannot happen here today. Replay (scratch copy of this tree): inside `reading_tree()`, after `set_field` then a raw `write_text` of `status:`, `inventory.grain(...).status` still reads `zzz-apply`. A new `ft-probe-new.md` is `None` inside the scope and found outside it. Fix: after any spawn in `run_gates`, drop the held snapshot (a one-line `inventory.forget_tree()`, or bump a counter `_held` compares), plus one case. About 5 lines.
- **N1 NIT** `repo/pm/ledger.py::append_to`: `apply.mutations()` does not count this append. It is harmless because no `_held` key covers a `.jsonl` file (pool scans keep only `.md`). It becomes a stale read the day a ledger read is held.
- **N2 NIT** `tests/test_pm_inventory_scale.py`: the 20 s budgets are about 50x the measured 0.4/1.1 s, not the brief's 5x. The docstring gives the reason (load 90-100) and the walk count `{1}` per pool is the real guard. Accepted as written.
- **N3 NIT** `core/walk.py::_WALKS`: process-global instrumentation on the production path, keyed by root, never cleared. It is cheap. A test that reads `walks()` in-process must diff before/after, not read absolutes (the scale case uses a child, so it is fine).

`pool_walk` now returns `descendants` order: `sorted(rglob)` plus filters that keep order. I checked it on this tree: `pool_walk == sorted(pool_walk)` for all 4 pools (21/124/114/69 files). `children` returns index order, which is the order the old list comprehension gave. No output order changed.
